# Business Context Maps: HTML maps inside context skills

> Cited by the business context map skills (`CONTEXT_MAP_SKILLS` in `cli/lib/context-maps.ts` is the one list), by their generator (`project-context` modes `data`, `features` and `api`), by `./skill-scaffold.md` §3 (the principle) and by `./skill-resolver.md` rule 5 (who loads them). This file is SYNCED: the procedure improves for every project, while each skill folder, its map and its `refresh.md` are the project's own.

---

## 1 · Why a map lives in a skill, not in `.context/`

`.context/` holds what a SCRIPT pulls from a source of truth (Jira, the OpenAPI spec) plus what this repo itself is the source of truth for (PRD, SRS, ADRs, the domain glossary, the master design plan). A business map is neither: an AI reads the code, the database schema and the API contract and writes a synthesis. Two sessions would write it differently and rebuilding it costs thousands of tokens, so it is authored knowledge, and authored knowledge that must arrive unasked is a skill (`./skill-scaffold.md` §3).

So each business map is ONE HTML file inside its context skill, at `references/<map>.html`:

| Skill | Map | Aspect | Generator |
|---|---|---|---|
| `business-data-context` | `business-data-map.html` | entities, relationships, RLS, migrations, state machines, automatic processes, integrations | `project-context` mode `data` |
| `business-feature-context` | `business-feature-map.html` | feature catalog, CRUD matrix, UI inventory, feature flows | `project-context` mode `features` |
| `business-api-context` | `business-api-map.html` | auth model, route groups, OpenAPI surface, critical API journeys | `project-context` mode `api` |

A human opens a map in a browser (`bun run context:map <slug> --open`); the AI reads it through `bun run context:map` (§3). There is no markdown twin and no second copy: the twin is always the one that drifts. The authored sources stay where they are: PRD and SRS under `.context/`, the glossary hand-kept in `.context/business/domain-glossary.md`. There is no domain map and no infrastructure map.

## 2 · Anatomy (the contract the generator writes and the reader parses)

| Part | Rule |
|---|---|
| Line 1 | a generated map: `<!-- generated by <generator>; edited in place by <slug> refresh; do not hand-edit -->`. A placeholder: `<!-- placeholder: run <generator> to generate this map -->`. `<generator>` is the entry's `generator` in `CONTEXT_MAP_SKILLS`, verbatim (`project-context mode data`). The reader, the updater and the doctor read ONLY this line to tell the two apart |
| `<head>` | `<title>`, inline `<style>` only, no external script, so the file opens from `file://`. A Google Fonts `<link>` is allowed (diagram-design's own typography) |
| Sections | flat `<section id="<stable-slug>" data-sources="<sources>" data-updated="YYYY-MM-DD">`, never nested. One section per fact unit: one entity, one flow, one feature, one route group. Each opens with an `<h2>`. The id is the edit anchor and never changes after CREATE |
| `data-sources` | comma-separated signals the section was built from. The generic set: repo paths (`src/app/api/orders/`), `db:<table>`, `migration:<file>`, `openapi:<tag or path>`, `route:<path>`. The set is open: each map skill's `references/refresh.md` may declare more prefixes for its aspect (for example `cron:<job>`, `auth:<scheme>`) with their own staleness rule. The staleness check (§5) reads them |
| Body | plain semantic HTML: `<p>`, `<ul>`, `<table>`, `<h3>`, `<code>`. No fact lives only inside a diagram: every fact a figure shows is also in the text |
| Figures | `<figure data-diagram="<type>" data-for="<section-id>">` wrapping a diagram-design inline SVG and a `<figcaption>`. One overview figure at the top of the map, then a per-section figure only where a picture carries the mechanism (diagram-design's own budget: above nine nodes, split) |
| Last section | `<section id="discovery-gaps">`: what could not be verified. "I could not verify X" beats an invented answer |
| Provenance | a section migrated from a legacy markdown map carries `data-migrated-from="<path>"` once, dropped the first time the section is regenerated |

A generated map legitimately contains counts (tables per schema, routes per group): it is a generated artifact, exempt from Critical Rule #17 like every generated file (`./volatile-facts.md`).

## 3 · Reading a map (the AI never reads the raw HTML)

Inline SVG is most of a map's bytes and none of its facts. Read through the reader, never with a file read:

| Need | Command |
|---|---|
| the whole map as text | `bun run context:map <slug>` |
| one section (a dispatch that touches one entity or one route group) | `bun run context:map <slug> --section <id>` |
| the index for a staleness check | `bun run context:map <slug> --list` (id · updated · sources) |
| the rendered map, for a human | `bun run context:map <slug> --open` |

A placeholder map prints a notice naming its generator and exits 0: treat it as "no map", never as an empty system. A briefing injects the COMMAND, not the file path (`./skill-resolver.md` rule 5).

## 4 · Generating and updating (owned by `project-context`)

| State | What runs | Writes |
|---|---|---|
| map absent or placeholder | the mode's CREATE: every section from the sources; the legacy markdown map the skill replaces (the entry's `legacy` list in `CONTEXT_MAP_SKILLS`, a `.context/business/business-*-map.md` an older project generated) is read as INPUT when present and cited in `data-migrated-from` | the whole file, once |
| map generated | the mode's UPDATE: run the staleness check (§5), regenerate ONLY the stale sections, show a section-level diff, WAIT for approval | the approved sections only |
| a section's facts changed and it has a figure | redraw that figure only | one `<figure>` |

No path regenerates a whole generated map. That is the token saving, and the section id is what makes it mechanical: an edit over one `<section>` block.

The legacy markdown maps are never deleted by any of this. They stay where a project committed them and are read as input.

## 5 · Staleness check

For each section from `--list` (the generic prefixes below; an aspect's extra prefixes are checked by its own `references/refresh.md`):

- a repo path in `data-sources` → `git log --since=<data-updated> --oneline -- <path>`; any commit → stale.
- `db:<table>` or `migration:<file>` → a migration under `stack.database.migrations_dir` (when the app keeps one) since the date, or `[DB_TOOL]` (capability `db`) shows a column, constraint, policy or trigger the section does not describe.
- `openapi:<x>` → the contract changed since the date (`bun run api:sync` output, or the spec file's `git log`).
- `route:<path>` → the route handler or page file changed since the date.
- any other prefix → the rule the map skill's `references/refresh.md` declares for it; a prefix no `refresh.md` declares is reported as `unknown`, never silently fresh.

A section with no declared sources is reported as `unknown`, never silently fresh.

## 6 · Self-update from a session (the context skill's own write path)

A context skill does not run workflows. It DOES keep its own map honest: when a session observes something that contradicts a section (a query shows a column the map omits, a route answers a status the map says is impossible, a screen has a CRUD action the matrix lacks), the skill PROPOSES the edit and applies it only on approval.

1. **Locate**: `bun run context:map <slug> --list`, then `--section <id>` for the section the observation touches.
2. **Evidence**: the observation that contradicts it, measured (a query, a request, a file path at a commit, a session label). No evidence, no proposal.
3. **Propose** to whoever owns the session: the user in the main thread, or the conductor when the session is a supervised worker (through the channel it already reports on; a one-shot subagent puts the proposal in its report instead). The proposal names the skill, the section id, the evidence and the before/after text in one message.
4. **Apply on approval only**: re-read the section (another session may have edited it), edit that ONE `<section>` block, set `data-updated` to the date of the edit, add any new signal to `data-sources`, redraw its figure only if the figure's facts changed (§7).
5. **Verify**: `bun run context:map <slug> --section <id>` prints the new text.

Scope: the skill writes files under its OWN `references/` and nowhere else (`metadata.writes: [references/]`, gated by `scripts/lint-skills.ts` `CONTEXT-WRITES`). It never touches Jira, another skill, `.context/` or product code. A proposed rule of judgment (not a fact) goes to `## Rules` or `references/gotchas.md` through the same approval, dated and measured (`./skill-scaffold.md` §3).

## 7 · Diagrams: capability `diagrams`

Figures are drawn with the diagram-design skill (installed at project level by `cli/install.ts`; a user-level install or a harness plugin satisfies it too). Capability `diagrams` resolves by the SKILL's presence, not by an MCP tool (`./mcp-capabilities.md` §2): before drawing, check that a `diagram-design` skill is loadable. Absent → STOP at the point of use and name the install line (`bunx skills add https://github.com/cathrynlavery/diagram-design --skill diagram-design --yes`); never ship a map with hand-drawn SVG or ASCII in its place (`./mcp-capabilities.md` §4).

Style is diagram-design's business. Its own `.diagram-design` marker at the repo root (`profile: <slug>`) selects a saved profile when a project wants one; without it the skill runs its own first-run gate. The repo records nothing else about style: two machines may render different skins, and the information in the text is what matters.

## 8 · Where a human sees the maps

`bun run context:map <slug> --open` hands the map file to the system browser. The file is self-contained (§2), so there is no server and no copy under `docs/`: the browser and the AI read the same file.

## 9 · Delivery and the updater

The skills listed in `CONTEXT_MAP_SKILLS` are the one exception to "every `<aspect>-context` is project-local" (`isProjectLocalSkillPath` in `cli/lib/updater-core.ts`): `bun sync` DELIVERS a skill's folder once when it is absent (`collectContextMapBootstrap`), then never overwrites or deletes anything inside it. A missing or placeholder map, with any legacy markdown map of its `legacy` list beside it, produces an informational parity row (never blocking), and `bun run setup:doctor` prints the same line.
