# Artifact Lifecycle — which status every dev artifact lives in, who moves it, and what to do when the slug is missing

> Shared doctrine cited by every workflow skill that creates or transitions a tracker issue
> (`sprint-development`, `autonomous-delivery`, `product-management`). Companion to
> `session-footer-contract.md` Part 3 (the light stage verifier that checks the outcome) and
> `acli-integration.md` (the HOW of a transition). Where the verifier asks *did the issue reach
> the status this stage meant to reach*, this file says **which status that is, which transition
> slug gets it there, and who owns firing it.**
>
> **Load this before firing any transition.** The slugs below are the only valid
> `{{jira.status.<type>.<slug>}}` / `{{jira.transition.<type>.<slug>}}` references. They are
> declared in `.agents/jira-required.yaml` (`work_types.<type>.required_statuses` /
> `required_transitions`) and resolve to workspace ids in `.agents/jira-workflows.json`
> (generated by `bun run jira:sync-workflows`).

## Why this file exists

An issue that is worked and never moved is indistinguishable from an issue nobody worked on. A
story still `In Progress` after its PR merged tells the PM the work is open; a bug still `Open`
after its fix shipped tells QA there is nothing to retest. The dev loop leans on tracker
automation (PR opened → `In Review`, merge → `Ready For QA`) that fires inconsistently, so a
skill that assumes the automation handled it strands the issue silently.

The second failure is the opposite one: a skill that does not find the transition it expected
and **guesses** one (a remembered id, a status name from another project, a hand-edited
catalog). That moves the issue somewhere real and wrong. This file closes both: every move a
dev skill owns is named here by slug, and §4 is the only way to handle a slug that is not there.

## 1. The lifecycle table

Read a row as: **this artifact is born HERE, this stage moves it THERE, and it ends HERE.**
"Created in" is whatever the work type's `create` transition lands on: Jira decides that, not
the skill. Everything after that a dev skill fires is listed; everything it does NOT fire is
named as someone else's.

| Artifact | Work type | Created by | Created in | Moved by → target (transition slug) | Terminal |
|---|---|---|---|---|---|
| **Epic** | `epic` | `/product-management` (epic creation, add-feature) | `backlog` | `/product-management` right after create: `plan` → `planning` (`statuses.epic_default`). **No dev skill moves an epic past that**: `ready_to_work` and `complete` belong to the PO / team. The Epic precheck reads the epic, it never transitions it | `done` |
| **Story** | `story` | `/product-management` (add-feature, story refinement; `autonomous-delivery` `discovery` routes through it) | `backlog` | `/product-management` after create: `analyze` → `shift_left_qa` (`statuses.story_default`) · QA shift-left + team own `estimate` → `estimation` and `estimated_and_ready_to_work` → `ready_for_dev` · `/sprint-development` Stage 1 end: `start_working` → `in_progress` · Stage 3 (PR opened): automation fires `pull_request` → `in_review`; **if it did not fire, the stage fires it** · Stage 4 (merged + staging deploy green): automation fires `deployed` → `ready_for_qa`; if not, the stage fires it · QA owns `start_testing` / `qa_sign_off`; release owns `include_in_release` / `released` | `deployed_to_production` (released by the team, never by a dev skill) |
| **Bug** (also `defect`, `improvement`) | `bug` / `defect` / `improvement` | QA or a reporter (external); a Stage 3 review may file one under the parent story | `open` | `/sprint-development` bug-fix triage: real bug `start_fixing` → `in_progress` · duplicate `is_duplicated` → `duplicated` · works as designed `is_wad` → `rejected` · enhancement `is_not_a_bug` → `enhancement` · cannot reproduce `is_cnr` → `cannot_reproduce` · low priority `defer` → `deferred` · PR opened: `pull_request` → `in_review` · merged + deployed: `fixed_and_deployed` → `ready_for_qa` · urgent hotfix with no review step: `hard_pushed` → `ready_for_qa` · QA owns `retest_passed` → `closed` | `closed` (or a triage terminal) |
| **Tech Story / Tech Debt** | `tech_story` / `tech_debt` | dev / PM (external) | `to_do` | `/sprint-development` Stage 1 end: `start_working` → `in_progress` · Stage 3 (PR opened): `ready` → `in_review` · merged with no QA scope: `complete` → `completed` · QA owns `test_finished` → `automated` when the item carried test scope | `completed` / `automated` |
| **Feature Implementation Plan** | field `feature_implementation_plan` on the Epic | `/sprint-development` Stage 1 (macro plan, `references/feature-plan.md`) | — (a field, not an issue) | authored in-session → pushed to the field (or its `## Feature Implementation Plan (Dev)` fallback comment) → `bun run jira:sync-issues get <EPIC>` → read back from the synced `feature-implementation-plan.md`. Re-pushed when the plan changes; never hand-written locally (`.agents/instructions/agent-local-context-pbi.md` §9) | the field |
| **Spec Implementation Plan** | field `spec_implementation_plan` on the Story | `/sprint-development` Stage 1 (`references/story-plan.md`) | — | same push → sync → read-back loop; re-pushed at the Stage 1 → Stage 2 gate when `/git-flow-master` resolves the chain strategy | the field |
| **Pull request** | GitHub PR | `/sprint-development` Stage 3 via `/git-flow-master` | open, against the strategy's default base | Stage 4 merges it **only after the user's OK** (never auto-merge) · abandoned work: closed unmerged by the user | merged (or closed) |
| **Staging deploy** | deployment for the merged SHA | CI on merge to the integration branch | building | `/sprint-development` Stage 4 polls the deployment for that commit SHA (`/vercel-cli`) until it reads `READY` | `READY` (or failed → Stage 4 stops) |
| **Production deploy** | deployment for the released SHA | `/sprint-development` Stage 5, gated on QA green + business approval | building | Stage 5 watches the health window; KPIs red → `references/rollback-plan.md` | `READY` (or rolled back) |

**A row is where the artifact must END UP for the stage to be done, not a promise the move is
free.** A mapped, available transition can still be refused by the instance's own validators:
that is §4.2, not a reason to leave the issue behind.

### 1.1 Edges that do not exist — do not look for them

The catalog is the authority. Route around these, never invent an id:

- **A story transition from `in_review` back to `ready_for_dev`.** Review feedback keeps the
  story `in_review` while Stage 2 loops; `back_from_in_progress` only exists from `in_progress`.
- **A `story` move past `ready_for_qa` by a dev skill.** `start_testing`, `qa_sign_off`,
  `include_in_release` and `released` exist, and none of them is a dev skill's to fire. Stage 5
  shipping to production does not move the story: the release owner does.
- **A bug status named `Need Info`.** The bug workflow has `cannot_reproduce`, `deferred` and a
  comment; a "need more information" outcome is a comment plus whichever of those the user picks.
  A project that does have such a status is the §4 case, not a reason to hard-code its name.

Transitions the catalog lists that no stage fires (`aborted`, `recover`, the `back_from_*`
family, `re_open`) are legitimate for a project to use by hand; no skill fires them on its own.

## 2. Ownership rule — read the assignee around every transition

**The dev harness does not set an assignee at create.** Epics and stories are created
unassigned (`/product-management`); the team assigns work. Only the hand-offs below move the
assignee, and each one is explicit.

**A transition can reassign the issue behind your back.** Tracker automation and workflow
post-functions are invisible in the transition catalog. The one this harness already relies on
having observed: **merge automation assigns the merged story to the developer**, while Stage 4's
rule says a story at `ready_for_qa` belongs to its shift-left QA owner. So on every transition a
dev skill fires or verifies:

1. **Read `assignee` before firing.** The same issue read that lists the available transitions
   returns it (`bun run jira:sync-issues get <KEY>`).
2. **Read it back after.** An automation that fires late (Stage 3 / Stage 4) is read back when
   its status change is confirmed, not when the merge lands.
3. **If the transition moved it** and the stage has no hand-off rule for that status, **restore
   the previous owner** and record the post-function in the `progress.md` checkpoint. Where the
   stage does have a rule (Stage 4 → shift-left QA owner, or unassigned when none can be
   identified), apply the rule, never the automation's choice.
4. **Verify the write landed.** Some CLI assignment paths report success while CLEARING the
   field (`sprint-development` Stage 4 gotchas); the read-back is the only proof.

**Before editing an issue someone else owns** to make a write go through: ask the user. Taking
ownership silently is not a fix; a declined reassignment is reported as blocked, naming the owner.

## 3. Who fires a transition the automation was supposed to fire

Stage 3 (`pull_request`) and Stage 4 (`deployed` / `fixed_and_deployed`) normally ride on the
tracker's automation. That automation is a convenience, never a guarantee (`autonomous-delivery`
hazard catalogue: it fires late, twice, or not at all, and it fires on internal PRs of a chain
whose base is not the integration branch). So:

- **Check the live status after the event**, every ticket, every type. A status flip proves
  nothing about git: the integration branch does (`git merge-base --is-ancestor`).
- **Not fired → the stage fires the mapped slug itself** and says so in the stage report.
- **Fired on the wrong event** (a chain's internal merge moved the story to `ready_for_qa` while
  nothing reached the integration branch) → report it with both facts; moving it back is a
  `back_from_*`-shaped manual call, which the user makes.

## 4. Unmapped-status fallback protocol — never strand an issue, never guess an id

A project that renamed its statuses, uses a synonym, or runs against a stale catalog must not
end up with silently un-transitioned issues. When a transition is needed:

1. **Resolve** `{{jira.transition.<type>.<slug>}}` from `.agents/jira-workflows.json`. Present →
   fire it with `[ISSUE_TRACKER_TOOL]` and move on. The primary CLI matches by target status
   NAME; when two transitions land on the same status, fire by the resolved id instead (`acli`
   skill, `references/gotchas.md` §9 holds the HOW).
2. **Slug ABSENT for that work type** → do NOT skip silently and do NOT guess. Ask
   `[ISSUE_TRACKER_TOOL]` for the LIVE transitions available from the issue's current status
   (same section of the `acli` gotchas).
3. **Pick the closest candidate by name** with the synonym table (§4.1) and present **ONE**
   question through the harness's own prompt:

   > `{KEY}` needs to move to **`<intended status>`**, but this project has no mapped
   > transition `<slug>` for work type `<type>`. Live transitions from `<current status>`:
   > **A** `<name>` → `<target>` · **B** `<name>` → `<target>`.
   > Transition via **`<best guess>`**? *yes* / *pick another* / *skip (leave it in `<current status>`)*

   A batch that hits the same unmapped slug on several issues asks once and applies the answer
   to the rest of the batch.
4. **On yes**: execute with the **live id** (never a name from memory, never an id from another
   project or an old doc), record the executed transition in the session `progress.md`
   checkpoint, and **recommend** `bun run jira:sync-workflows` then `bun run jira:check` so the
   next session resolves it at step 1. **Never hand-edit `.agents/jira-workflows.json`**: it is
   generated.
5. **On skip**: the issue stays where it is, and the light stage verifier records that line as a
   stated N/A with the reason (`transition_skipped: <slug>` in a skill report that uses that
   key). A skip the user chose is fine. A skip nobody saw is the bug this file exists to kill.
6. **Unattended run** (`autonomous-delivery`, no human on the line): steps 1-2 run as written;
   step 3 is NOT answered by the run itself. Fire nothing, leave the issue where it is, and name
   the unmapped slug, the live candidates and the recommended re-sync as an explicit flag in the
   run report. Git stays the truth for what shipped, so a stranded status never blocks the run;
   it only must not disappear.
7. **Slug present but Jira REJECTS the transition** (permission, workflow condition, a validator
   demanding a field): report the **exact** error text, do NOT retry blindly, and run §4.2.

### 4.1 Synonym table — for step 3's best guess

| Intended slug | Common project names to match against |
|---|---|
| `in_progress` | In Progress · In Development · Doing · Started |
| `in_review` | In Review · Code Review · PR Open · Review |
| `ready_for_qa` | QA Ready · To Test · Ready to Test · Awaiting QA · Ready For Testing |
| `ready_for_dev` | Ready For Dev · Selected for Development · To Do · Ready |
| `planning` (epic) | Planning · Refinement · Discovery · Defined |
| `shift_left_qa` (story) | Shift-Left QA · QA Review · Refinement · Analysis |
| `completed` (tech items) | Completed · Done · Resolved · Closed |
| `cannot_reproduce` / `deferred` (bug) | Cannot Reproduce · CNR · Need Info · Deferred · Postponed · On Hold |

A match is a **suggestion to the user**, never an automatic choice. Present it, wait.

### 4.2 Mapped slug, gated by validators — the transition exists and Jira still says no

1. **Read the error in full.** A validator names the fields it wants. A *condition* failure
   (`you do not have permission`, `the issue is not assigned to you`) is different: check §2
   first, and taking ownership to force a move through is a question for the user, never automatic.
2. **Fill what the stage legitimately knows**, then re-fire ONCE. A bug fix's `root_cause` and
   `fix` type, the PR link, the deployed environment: the stage has real content for those, so it
   writes them and retries without asking.
3. **Never invent a value to satisfy a validator.** Story points, a severity, an estimation the
   stage does not actually know is fabricated data that outlives the session and is later read as
   the team's judgement.
4. **Whatever is left → ONE question**, naming the issue, the target status, the exact fields the
   validator demands and which of them the stage cannot answer: *fill them together now* /
   *leave it at `<current status>`* / *another route the user names*. Unattended: a flag in the
   run report, never an invented value.
5. **On leave**: the verifier line is a stated N/A quoting the validator's own words, never a
   blank and never a misleading "no transition available".
6. **Record it once per project, not once per issue.** A heavy validator set is screen
   configuration, not an incident: note it in `progress.md` the first time so later stages of the
   same run expect it, and raise it with the team. `bun run jira:sync-workflows` will NOT learn it:
   screens are not part of the transition catalog.

## 5. Closing every stage — the light verifier

The verifier itself lives in `session-footer-contract.md` Part 3; it is not redefined here. Two
of its lines read this file:

- **Tracker status**: the status this stage meant to reach is the §1 row for the artifact, and
  the line names the slug fired (by the stage or by automation it verified) or the stated reason
  it was not (§4 skip, §4.2 leave, unattended flag).
- **Assignee**: read back after every transition the stage fired or verified (§2). A transition
  that moved it with no hand-off rule and was not restored is a `NO`.

A stage owner lists only its stage-specific lines inline (which issue, which slug) and cites
Part 3 for the rest.
