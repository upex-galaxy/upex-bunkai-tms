# Artifact lifecycle: which status each dev artifact lives in, who moves it, and what to do when the slug is missing

> Shared doctrine for every workflow skill that creates or transitions a tracker issue (`sprint-development`, `autonomous-delivery`, `product-management`). It pairs with `session-footer-contract.md` Part 3 (the light stage verifier that checks the outcome) and `acli-integration.md` (how a transition is fired). The verifier asks whether the issue reached the status the stage meant to reach. This file says which status that is, which transition slug gets it there, and who owns firing it.
>
> Load it before firing any transition. The slugs below are the only valid `{{jira.status.<type>.<slug>}}` and `{{jira.transition.<type>.<slug>}}` references. They are declared in `.agents/jira-required.yaml` (`work_types.<type>.required_statuses` and `required_transitions`) and resolve to workspace ids in `.agents/jira-workflows.json`, generated by `bun run jira:sync-workflows`.

## Why this file exists

An issue that is worked and never moved looks the same as an issue nobody worked on. A story still `In Progress` after its PR merged tells the PM the work is open, and a bug still `Open` after its fix shipped tells QA there is nothing to retest. The dev loop leans on tracker automation (PR opened moves the issue to `In Review`, merge moves it to `Ready For QA`) that fires inconsistently, so a skill that assumes the automation did its job strands the issue silently.

The opposite failure is a skill that does not find the transition it expected and guesses one: a remembered id, a status name from another project, a hand-edited catalog. The issue then moves somewhere real and wrong. Every move a dev skill owns is named here by slug, and §4 is the only way to handle a slug that is missing.

## 1. The lifecycle table

Read a row as: the artifact is born in one status, a stage moves it to the next, and it ends in the terminal one. "Created in" is whatever the work type's `create` transition lands on, which Jira decides and the skill does not. Every move a dev skill fires is listed, and every move it does not fire is named as someone else's.

| Artifact | Work type | Created by | Created in | Moved by → target (transition slug) | Terminal |
|---|---|---|---|---|---|
| **Epic** | `epic` | `/product-management` (epic creation, add-feature) | `backlog` | `/product-management` right after create: `plan` → `planning` (`statuses.epic_default`). **No dev skill moves an epic past that**: `ready_to_work` and `complete` belong to the PO / team. The Epic precheck reads the epic, it never transitions it | `done` |
| **Story** | `story` | `/product-management` (add-feature, story refinement; `autonomous-delivery` `discovery` routes through it) | `backlog` | `/product-management` after create: `analyze` → `shift_left_qa` (`statuses.story_default`) · QA shift-left owns `refined` → `ready_for_dev` (`shift_left_qa` → `ready_for_dev`, AI Effort set first) · `/sprint-development` Stage 1 end: `start_working` → `in_progress` · Stage 3 (PR opened): automation fires `pull_request` → `in_review`; **if it did not fire, the stage fires it** · Stage 4 (merged + staging deploy green): automation fires `deployed` → `ready_for_qa`; if not, the stage fires it · QA owns `start_testing` / `qa_sign_off`; QA's `defect_reported` moves the story `in_test` → `blocked`, and the dev then fires `fix_defect` → `in_progress` on the Story, fixes, and re-delivers to `ready_for_qa` (`pushed`, or `pull_request` + `deployed`); `back_to_dev` (`blocked` → `ready_for_dev`) exists in the catalog and no stage fires it on its own; release owns `include_in_release` / `released` | `deployed_to_production` (released by the team, never by a dev skill) |
| **Bug** (also `defect`, `improvement`) | `bug` / `defect` / `improvement` | QA or a reporter (external); a Stage 3 review may file one under the parent story | `open` | `/sprint-development` bug-fix triage: real bug `start_fixing` → `in_progress` · duplicate `is_duplicated` → `duplicated` · works as designed `is_wad` → `rejected` · enhancement `is_not_a_bug` → `enhancement` · cannot reproduce `is_cnr` → `cannot_reproduce` · low priority `defer` → `deferred` · PR opened: `pull_request` → `in_review` · merged + deployed: `fixed_and_deployed` → `ready_for_qa` · urgent hotfix with no review step: `hard_pushed` → `ready_for_qa` · QA owns `retest_passed` → `closed` | `closed` (or a triage terminal) |
| **Tech Story / Tech Debt** | `tech_story` / `tech_debt` | dev / PM (external) | `to_do` | `/sprint-development` Stage 1 end: `start_working` → `in_progress` · Stage 3 (PR opened): `ready` → `in_review` · merged with no QA scope: `complete` → `completed` · QA owns `test_finished` → `automated` when the item carried test scope | `completed` / `automated` |
| **Feature Implementation Plan** | field `feature_implementation_plan` on the Epic | `/sprint-development` Stage 1 (macro plan, `references/feature-plan.md`) | n/a (a field, not an issue) | authored in-session → pushed to the field (or its `## Feature Implementation Plan (Dev)` fallback comment) → `bun run jira:sync-issues get <EPIC>` → read back from the synced `feature-implementation-plan.md`. Re-pushed when the plan changes; never hand-written locally (`.agents/instructions/agent-local-context-pbi.md` §9) | the field |
| **Spec Implementation Plan** | field `spec_implementation_plan` on the Story | `/sprint-development` Stage 1 (`references/story-plan.md`) | n/a | same push → sync → read-back loop; re-pushed at the Stage 1 → Stage 2 gate when `/git-flow-master` resolves the chain strategy | the field |
| **Pull request** | GitHub PR | `/sprint-development` Stage 3 via `/git-flow-master` | open, against the strategy's default base | Stage 4 merges it **only after the user's OK** (never auto-merge) · abandoned work: closed unmerged by the user | merged (or closed) |
| **Staging deploy** | deployment for the merged SHA | CI on merge to the integration branch | building | `/sprint-development` Stage 4 polls the deployment for that commit SHA (`/vercel-cli`) until it reads `READY` | `READY` (or failed → Stage 4 stops) |
| **Production deploy** | deployment for the released SHA | `/sprint-development` Stage 5, gated on QA green + business approval | building | Stage 5 watches the health window; KPIs red → `references/rollback-plan.md` | `READY` (or rolled back) |

A row is where the artifact must end up for the stage to be done, and the move is not guaranteed to be free. A mapped, available transition can still be refused by the instance's own validators. That is §4.2, and it is no reason to leave the issue behind.

### 1.1 Edges that do not exist

The catalog is the authority. Route around these edges and never invent an id for them:

- A story transition from `in_review` back to `ready_for_dev`. Review feedback keeps the story `in_review` while Stage 2 loops, and `back_from_in_progress` only exists from `in_progress`.
- A `story` move past `ready_for_qa` by a dev skill. `start_testing`, `qa_sign_off`, `include_in_release` and `released` exist, and none of them is a dev skill's to fire. The one dev move in QA's territory is the defect loop: after QA's `defect_reported` the story sits in `blocked`, and `fix_defect` (`blocked` to `in_progress`) is the dev's. Stage 5 shipping to production does not move the story, because the release owner does.
- A bug status named `Need Info`. The bug workflow has `cannot_reproduce`, `deferred` and a comment, so a "need more information" outcome is a comment plus whichever of those the user picks. A project that does have such a status is the §4 case, and its name is not hard-coded.

The catalog also lists transitions that no stage fires (`aborted`, `recover`, `back_to_dev`, the `back_from_*` family, `re_open`). A project may use them by hand, and no skill fires them on its own.

## 2. Ownership: read the assignee around every transition

Epics and stories are created unassigned by `/product-management` and the team assigns work. The native `assignee` names the current holder of the issue. The one hand-off a dev skill owns happens when a Story reaches `ready_for_qa`: the dev moves `assignee` to the QA named in `{{jira.qa_assignee}}`, the record of the QA who followed the story since shift-left (read it, never overwrite it). When `qa_assignee` is empty, the dev leaves `assignee` as it is, says so in the QA notification comment and does not guess a QA.

A transition can reassign the issue behind your back, because tracker automation and workflow post-functions do not appear in the transition catalog. The one this harness has observed is that merge automation assigns the merged story to the developer, while Stage 4's rule puts a story at `ready_for_qa` with the QA. So on every transition a dev skill fires or verifies:

1. Read `assignee` before firing. The same issue read that lists the available transitions returns it (`bun run jira:sync-issues get <KEY>`).
2. Read it back after. An automation that fires late (Stage 3 or Stage 4) is read back when its status change is confirmed, not when the merge lands.
3. If the transition moved it and the stage has no hand-off rule for that status, restore the previous owner and record the post-function in the `progress.md` checkpoint. Where the stage does have a rule (Stage 4 at `ready_for_qa`: the `{{jira.qa_assignee}}` QA, or the current holder when it is empty), apply the rule and ignore the automation's choice.
4. Verify the write landed. Some CLI assignment paths report success while clearing the field (`sprint-development` Stage 4 gotchas), so the read-back is the only proof.

Editing an issue someone else owns, just to make a write go through, is a question for the user: taking ownership silently is not a fix. A supervised worker asks its conductor. A routine with nobody, or a declined reassignment, reports the issue as blocked and names the owner.

## 3. Who fires a transition the automation was supposed to fire

Stage 3 (`pull_request`) and Stage 4 (`deployed`, `fixed_and_deployed`) normally ride on the tracker's automation. That automation is a convenience and never a guarantee: it fires late, twice or not at all, and it fires on the internal PRs of a chain whose base is not the integration branch (`autonomous-delivery` hazard catalogue). So:

- Check the live status after the event, for every ticket and every type. A status flip proves nothing about git. The integration branch does (`git merge-base --is-ancestor`).
- When the automation did not fire, the stage fires the mapped slug itself and says so in the stage report.
- When it fired on the wrong event (a chain's internal merge moved the story to `ready_for_qa` while nothing reached the integration branch), report it with both facts. Moving it back is a `back_from_*`-shaped manual call, which the user makes.

## 4. Unmapped-status fallback protocol: never strand an issue, never guess an id

A project that renamed its statuses, uses a synonym or runs against a stale catalog must not end up with silently un-transitioned issues. When a transition is needed:

1. Resolve `{{jira.transition.<type>.<slug>}}` from `.agents/jira-workflows.json`. When it is present, fire it with `[ISSUE_TRACKER_TOOL]` and move on. The primary CLI matches by target status name, so when two transitions land on the same status, fire by the resolved id instead (`acli` skill, `references/gotchas.md` §9 holds the how).
2. When the slug is absent for that work type, do not skip silently and do not guess. Ask `[ISSUE_TRACKER_TOOL]` for the live transitions available from the issue's current status (same section of the `acli` gotchas).
3. Pick the closest candidate by name with the synonym table (§4.1) and present one question through the harness's own prompt:

   > `{KEY}` needs to move to **`<intended status>`**, but this project has no mapped
   > transition `<slug>` for work type `<type>`. Live transitions from `<current status>`:
   > **A** `<name>` → `<target>` · **B** `<name>` → `<target>`.
   > Transition via **`<best guess>`**? *yes* / *pick another* / *skip (leave it in `<current status>`)*

   A batch that hits the same unmapped slug on several issues asks once and applies the answer to the rest.
4. On yes, execute with the live id, never a name from memory and never an id from another project or an old doc. Record the executed transition in the session `progress.md` checkpoint and recommend `bun run jira:sync-workflows` then `bun run jira:check`, so the next session resolves it at step 1. `.agents/jira-workflows.json` is generated, so a hand edit is overwritten and hides the gap.
5. On skip, the issue stays where it is, and the light stage verifier records that line as a stated N/A with the reason (`transition_skipped: <slug>` in a skill report that uses that key). A skip the user chose is fine. A skip nobody saw is the bug this file exists to kill.
6. Who answers step 3 depends on who is running:
   - A person is present: they answer, as above.
   - A supervised worker: the conductor holds the question and answers it, and the worker waits for that answer.
   - An unattended run (`autonomous-delivery`, nobody on the line): steps 1 and 2 run as written and the run does not answer step 3 itself. It fires nothing, leaves the issue where it is, and names the unmapped slug, the live candidates and the recommended re-sync as an explicit flag in the run report. Git stays the truth for what shipped, so a stranded status never blocks the run, and it must not disappear either (`decision-protocol.md`).
7. When the slug is present and Jira rejects the transition (permission, workflow condition, a validator demanding a field), report the exact error text, do not retry blindly, and run §4.2.

### 4.1 Synonym table for step 3's best guess

| Intended slug | Common project names to match against |
|---|---|
| `in_progress` | In Progress · In Development · Doing · Started |
| `in_review` | In Review · Code Review · PR Open · Review |
| `ready_for_qa` | QA Ready · To Test · Ready to Test · Awaiting QA · Ready For Testing |
| `ready_for_dev` | Ready For Dev · Selected for Development · To Do · Ready |
| `planning` (epic) | Planning · Refinement · Discovery · Defined |
| `shift_left_qa` (story) | Shift-Left QA · QA Review · Refinement · Analysis |
| `completed` (tech items) | Completed · Done · Resolved · Closed |
| `cannot_reproduce` / `deferred` (bug) | Cannot Reproduce · CNR · Need Info · Deferred · Postponed · On Hold |

A match is a suggestion to the user and never an automatic choice. Present it and wait for the answer (the §4 step 6 paths apply).

### 4.2 Mapped slug, gated by validators: the transition exists and Jira still says no

1. Read the error in full. A validator names the fields it wants. A condition failure (`you do not have permission`, `the issue is not assigned to you`) is different: check §2 first, and taking ownership to force a move through is a question for the user, never automatic.
2. Fill what the stage legitimately knows, then re-fire once. A bug fix's `root_cause` and `fix` type, the PR link and the deployed environment are content the stage has, so it writes them and retries without asking.
3. Do not invent a value to satisfy a validator. A token-usage figure, a severity or an effort level the stage does not actually know is fabricated data that outlives the session and is later read as the team's judgement.
4. Whatever is left becomes one question, naming the issue, the target status, the exact fields the validator demands and which of them the stage cannot answer: *fill them together now* / *leave it at `<current status>`* / *another route the user names*. A supervised worker sends it to its conductor. An unattended run puts it in the run report as a flag and never invents a value.
5. On leave, the verifier line is a stated N/A quoting the validator's own words, never a blank and never a misleading "no transition available".
6. Record it once per project, not once per issue. A heavy validator set is screen configuration and not an incident: note it in `progress.md` the first time so later stages of the same run expect it, and raise it with the team. `bun run jira:sync-workflows` will not learn it, because screens are not part of the transition catalog.

## 5. Closing every stage: the light verifier

The verifier lives in `session-footer-contract.md` Part 3 and is not redefined here. Two of its lines read this file, and a third applies to Stage 4:

- Tracker status: the status the stage meant to reach is the §1 row for the artifact, and the line names the slug fired (by the stage, or by automation the stage verified) or the stated reason it was not (§4 skip, §4.2 leave, unattended flag).
- Assignee: read back after every transition the stage fired or verified (§2). A transition that moved it with no hand-off rule and was not restored is a `NO`.
- Token usage: `{{jira.development_token_usage}}` is cumulative and optional. When the story is verified at `ready_for_qa` (and again after each fix loop), read the current value, add this cycle's measured delta (K = input plus output tokens, cache reads apart), never overwrite it, and post one `DTU cycle N: +x K (total y K) source=<harness or human>` comment. When no figure is available, the line is a stated N/A with the reason and never a `NO`; the same holds for an item that never reaches `ready_for_qa`. Tokens are measured and never estimated.

A stage owner lists only its stage-specific lines inline (which issue, which slug) and cites Part 3 for the rest.
