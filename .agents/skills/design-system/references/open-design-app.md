# Path C: Open Design app (local desktop UI)

> Opt-in path. The user iterates visually in a local app, then the result goes through Path E to become the final `DESIGN.md`.

## Purpose

Use this path when the user wants to iterate visually before locking tokens: try palette variants, play with compositions, see live HTML/PDF/PPTX previews, all local. Open Design (nexu-io, Apache-2.0) is open source, free, with no signup and no SaaS lock-in. It shares the brand catalog with `getdesign` (Path B) and adds an interactive visual Q&A layer on top. The UI does not emit a native `DESIGN.md`. It produces HTML/PDF/PPTX/ZIP/Markdown artifacts, and Path E converts them to the Google Labs spec.

> The product moves fast and the repo README usually runs ahead of the published release (see "README drift" below). Before you cite a behavior from this file, check the installed version (`GET /api/health` returns `version`). When the two disagree, the real binary wins and this doc gets updated.
> For screen mockups (the screen-mapping phase), the user pastes the `BRIEF.md` generated by `references/screen-design-brief.md` into the Discover / brief field.

## Install: pick one of three routes

The main surface is an **Electron desktop app with a local-first daemon**. Docker still exists but is no longer the recommended route, and this path does not need it.

| Route          | Requirements                    | When                                                          |
| -------------- | ------------------------------- | ------------------------------------------------------------- |
| Desktop app    | none (signed binary)            | Default. No Docker, no Node version conflicts.                |
| Docker Compose | Docker Desktop / docker-ce      | Only if the user already lives in containers or wants remote access. |
| From source    | Node `~24.x` + pnpm `10.33.x`   | Only to hack on Open Design's own code.                       |

### Route 1: desktop app (recommended)

Release assets (GitHub Releases or `open-design.ai`): a `.dmg` for macOS (arm64 and x64) and an `.exe` installer for Windows. If the release has no Linux AppImage, there is none, even when the README lists it as optional.

Download, verify the hash published next to the asset, then mount and install:

```bash
V=<version>   # tag of the release to install, from GitHub Releases
BASE="https://github.com/nexu-io/open-design/releases/download/open-design-v$V"
curl -sL -O "$BASE/open-design-$V-mac-arm64.dmg.sha256"
curl -L  -O "$BASE/open-design-$V-mac-arm64.dmg"
shasum -a 256 -c "open-design-$V-mac-arm64.dmg.sha256"   # must say: OK

hdiutil attach -nobrowse -readonly "open-design-$V-mac-arm64.dmg"
cp -R "/Volumes/Open Design/Open Design.app" /Applications/
hdiutil detach "/Volumes/Open Design"
```

Verify the signature before opening the app. The official build is **notarized by Apple**, so there is no Gatekeeper to bypass and no `xattr -d com.apple.quarantine` to run. If the assessment does not say `Notarized Developer ID`, stop and do not open it:

```bash
spctl -a -vvv "/Applications/Open Design.app"
# expected:
#   accepted
#   source=Notarized Developer ID
#   origin=Developer ID Application: Wei Huang (236R69AWW2)
```

Bundle id `io.open-design.desktop`. The installed app weighs hundreds of MB because it bundles the catalogs (design systems, skills, design templates, plugins). `list_skills` and `list_plugins` give the real catalog.

### Route 2: Docker Compose

Check for Docker before cloning anything (`docker --version`). If it is missing: macOS `brew install --cask docker`, Linux `apt-get install docker.io docker-compose-plugin`, Windows Docker Desktop.

```bash
git clone https://github.com/nexu-io/open-design /tmp/open-design
cd /tmp/open-design/deploy
cp .env.example .env
echo "OD_API_TOKEN=$(openssl rand -hex 32)" >> .env
docker compose up -d
# UI at http://localhost:7456
```

The real env vars (the `OPEN_DESIGN_*` names an earlier version of this doc listed **do not exist**):

- `OD_API_TOKEN` is required on Docker deploys. Without it the daemon has no auth gate.
- `OD_PORT` is the daemon port, default `7456`.
- `OD_BIND_HOST` is the bind interface, default `127.0.0.1`. Set it to a specific IP (for example a Tailscale address) to limit access to that interface.
- `OD_ALLOWED_ORIGINS` is needed behind a reverse proxy.
- `OD_ALLOWED_INTERNAL_HOSTS` is the allowlist for self-hosted model endpoints (the daemon has SSRF protection and blocks them by default).

### Route 3: from source

```bash
git clone https://github.com/nexu-io/open-design /tmp/open-design
cd /tmp/open-design
corepack enable && pnpm install
pnpm tools-dev run web
```

It needs Node `~24.x`. With a global Node 26 you have to isolate it (`nvm` / `mise` / `fnm`), and `corepack` does not ship with a Homebrew Node. The port is assigned dynamically, not 7456.

## Runtime: where everything lives (desktop app)

This matters for the bridge to Path E and for debugging. The app does not write into the user's project or into `./.od/`.

```
~/Library/Application Support/Open Design/
  installation.json
  namespaces/release-stable/
    data/
      app-config.json        # onboarding, chosen agent, design system, telemetry
      app.sqlite             # projects, conversations, messages, runs, templates
      projects/              # <-- generated artifacts, per project
      artifacts/  brands/  library/  memory/  plugins/  connectors/
    logs/{desktop,daemon,web,launcher}/latest.log
    runtime/desktop-root.json
```

**The port is dynamic, not 7456.** The desktop app starts three processes (desktop, daemon, web sidecar), and each takes a free port at startup, different every session. The daemon publishes its own in its log:

```bash
tail -20 ~/Library/"Application Support"/Open\ Design/namespaces/release-stable/logs/daemon/latest.log
# ...{"state":"running","desktopAuthGateActive":true,"url":"http://127.0.0.1:50027"}
curl -s http://127.0.0.1:50027/api/health   # {"ok":true,"version":"0.16.1"}
```

The processes coordinate over Unix sockets in `/tmp/open-design/ipc/release-stable/{daemon,desktop,web}.sock`. That is why `lsof` on 7456 comes back empty with the desktop app: that port belongs to the web/Docker daemon mode only.

**Telemetry is on by default.** `app-config.json` starts with `telemetry.metrics: true` and `telemetry.content: true` (the second one sends content, not just metrics), relayed to `telemetry.open-design.ai` and PostHog. `artifactManifest` does start as `false`. If the project brief is sensitive, tell the user to turn telemetry off in Settings → Privacy before pasting product context.

## CLI `od`

The binary lives inside the bundle and runs on the system Node:

```bash
OD_CLI="/Applications/Open Design.app/Contents/Resources/app/prebundled/daemon/daemon-cli.mjs"
node "$OD_CLI" --help
```

**Name collision.** `od` already exists on macOS and Linux (`/usr/bin/od`, the coreutils octal dump), so do not alias `od` blindly. For a shim use another name (`odesign`) or an absolute path. The form the help itself recommends for agents is `"$OD_NODE_BIN" "$OD_BIN" tools ...`, precisely so nothing depends on PATH.

Subcommands useful here: `od tools directions` (prints the palette and font stacks of a design direction, ideal for the bridge), `od tools design-systems read`, `od export <file> --format pdf|image|pptx`, `od plugin`, `od automation`, `od diagnostics export`.

## MCP integration with the coding agent

`od mcp` starts a stdio MCP server that proxies to the running daemon. Do not run a bare `node <cli> mcp`: without more context the CLI falls back to `http://127.0.0.1:7456` (the Docker-mode port) and every tool call dies with `cannot reach the Open Design daemon`, because the desktop app uses a dynamic port.

The app publishes the canonical config under **Settings → MCP server**, so copy it from there. It skips the port entirely: it talks to the daemon over a Unix socket (`OD_SIDECAR_IPC_PATH`, a path that stays fixed between launches) and runs on the bundle's Electron Helper (`ELECTRON_RUN_AS_NODE=1`), not on the system Node. General shape (copy the real paths from Settings → MCP server):

```bash
claude mcp add-json --scope user open-design '{
  "command": "/Applications/Open Design.app/Contents/Frameworks/Open Design Helper.app/Contents/MacOS/Open Design Helper",
  "args": ["/Applications/Open Design.app/Contents/Resources/app/prebundled/daemon/daemon-cli.mjs", "mcp"],
  "env": {
    "OD_DATA_DIR": "$HOME/Library/Application Support/Open Design/namespaces/release-stable/data",
    "OD_SIDECAR_IPC_PATH": "/tmp/open-design/ipc/release-stable/daemon.sock",
    "ELECTRON_RUN_AS_NODE": "1"
  }
}'
claude mcp get open-design    # Status: ✔ Connected
```

`add-json` does not expand `$HOME`, so use the real absolute path as the app prints it. Claude Code loads MCP servers at startup: after registering, the user must **quit and reopen** the session before the `mcp__open-design__*` tools appear.

Register it with scope `user`, not `project`. It is a tool on the developer's machine, not a dependency of the repo, and it should not land in a shared `.mcp.json`.

The server announces its tools when it connects (projects, files, artifacts, skills, runs: for example `create_project`, `write_file`, `list_skills`, `start_run`, `get_run`). That list is the authority, not a copy here.

Four of them write or delete: `write_file`, `delete_file`, `delete_project`, `create_artifact`. `delete_project` is irreversible and requires `confirm: true`. Apply the normal confirmation rules before calling them.

The MCP needs the app open: with no daemon running, tool calls fail. When you omit `project`, `get_artifact` and `get_file` resolve against the project or file **active in the UI**, which makes "bring me the design I have open" very cheap.

### Preflight (app closed or MCP down)

Before any MCP flow, climb this ladder in order. Each rung has one concrete remedy.

1. **Are the MCP tools visible?** If `mcp__open-design__*` is not in the session, the server is not registered. Register it (config from Settings → MCP server, above) and tell the user to **restart the agent session**, since MCP servers load at startup. There is no mid-session workaround.
2. **Is the daemon alive?** Try a cheap tool (`list_projects`). If it fails with "cannot reach daemon", the app is closed. Launch it yourself and wait for the health check:

   ```bash
   open -ga "Open Design"    # -g: does not steal focus from the user
   LOG="$HOME/Library/Application Support/Open Design/namespaces/release-stable/logs/daemon/latest.log"
   for i in $(seq 1 30); do
     URL=$(grep -o '"url":"http://[^"]*"' "$LOG" | tail -1 | cut -d'"' -f4)
     [ -n "$URL" ] && curl -sf "$URL/api/health" >/dev/null && echo "daemon OK: $URL" && break
     sleep 2
   done
   ```

   Probe `list_projects` again once the health check passes.
3. **Is the app installed?** If `open -ga` fails (no `/Applications/Open Design.app`), install it with Route 1 above. That means a download plus signature verification, so report to the user and do not go ahead blindly when the network or the permissions are not there.
4. **MCP impossible but daemon reachable?** This happens for real: the MCP server drops mid-session (for example after an agent session limit) and cannot reconnect without a restart, while the app is still alive. The daemon exposes REST with the same operations. Contract (base = the URL from the daemon log, for example `http://127.0.0.1:50027`):

   ```bash
   curl -s $B/api/health                          # {"ok":true,"version":"0.16.1"}
   curl -s $B/api/projects                        # list
   curl -s -X POST $B/api/projects -H 'Content-Type: application/json' \
     -d '{"id":"<safe-id>","name":"<name>","designSystemId":"user:<slug>"}'
     # the field is designSystemId (NOT designSystem, which is silently ignored):
     # check that the response echoes it back non-null
   curl -s -X POST $B/api/runs -H 'Content-Type: application/json' -d @payload.json
     # payload: {"projectId":"...","message":"<prompt>","agentId":"claude","skillId":"frontend-design"}
     # fields = the start_run MCP ones under other names: prompt→message, agent→agentId, skill→skillId
   curl -s $B/api/runs/<runId>                    # status / agentMessage / artifactCount
   curl -s -X POST $B/api/runs/<runId>/cancel
   ```

   Gotcha: `POST /api/runs` with an empty body STARTS an orphan run (projectId null). Always pass projectId, and cancel any probe. This is an escape hatch, not the primary path: the MCP is the stable contract when it is connected.
5. **None of the above?** Degrade to the original manual flow: generate `BRIEF.md`, pause, and let the user iterate in the UI and tell you when they are done (the usual wait contract; see "Waiting for a person" below).

### Autonomous MCP flow: screen mockups end-to-end

The standard route when the screen-mapping phase (skill `design-system`) runs with the MCP available. The agent **commissions** the designs from Open Design and never writes them itself (S1 still holds: the one that generates is OD's pipeline, since `start_run` spawns its own internal agent with the OD skill). Prerequisite: the repo's design system installed as a `user:<slug>` user package (section "Install your design system as a user package (repo → OD)" below), so every generation inherits the real tokens.

1. **Project.** `create_project` with `designSystem: "user:<slug>"` and an `id` that is the batch slug (for example `<product>-<batch-slug>`). Check `designSystemId` in the response. On `400 DESIGN_SYSTEM_NOT_PUBLISHED`, run the PATCH publish (repo → OD section) and retry.
2. **OD skill.** For application screens use `frontend-design` ("application screens, production-grade"). `web-prototype` and `dashboard` do not exist in the catalog, so do not cite them. `list_skills` returns about 200KB: do not read it whole, grep the persisted file the harness leaves (`grep '"id":' <persisted>.txt`).
3. **One run per screen, sequential.** `start_run {project, skill, agent, prompt}` with the prompt = the per-screen slice of `BRIEF.md` (anatomy in `screen-design-brief.md` §MCP). Sequential, not parallel: screens 2..N must say "reuse the shell anatomy of screen 1", which needs the earlier screen to exist in the project's conversation (same `conversationId` = accumulated memory).
4. **Poll patiently.** `get_run(runId)` every 30 to 60 seconds. **The file can appear in `data/projects/<project>/` BEFORE the terminal status**, because the internal agent writes and keeps polishing. Do not export while `status: running`; wait for `succeeded`. For a cheap watcher that does not burn context (bash cannot call MCP), background a loop that tails the run's events log and exits when it sees the result:

   ```bash
   LOG="$HOME/Library/Application Support/Open Design/namespaces/release-stable/data/runs/<runId>/events.jsonl"
   for i in $(seq 1 60); do
     tail -5 "$LOG" 2>/dev/null | grep -q '"type":"result"' && echo TERMINAL && exit 0
     sleep 20
   done
   ```

5. **QA the artifact as each run closes.** Read `agentMessage` (the internal agent's self-report) and run sanity greps on the file: copy language, `lang=`, hex values outside the token block, presence of the exact slug. **Real gotcha:** the internal agent inherits the conversation's language, so if you orchestrate in Spanish the UI copy can come out in Spanish even when the prompt is in English. The fix is an explicit "UI copy in ENGLISH" constraint in EVERY prompt, plus a correction run at the first slip that also persists the rule (OD supports `rule-proposal` cards that become a project rule and self-check in later runs).
6. **The user's own runs in between.** The user can trigger their own runs from the UI (for example the OD skill `impeccable-design-polish` on a screen). Before exporting, list the runs by mtime again (`ls -lt .../data/runs | head`) and wait for the terminal of the LAST run that touches the file. Exporting in the middle of the user's polish overwrites their work.
7. **Export to the repo.** `cp` from `data/projects/<project>/<slug>.html` to `.context/designs/<project-slug>/<batch-slug>/` (the screen-mapping phase's drop zone). The MCP does not write outside its data root, so the `cp` is yours. After the whole batch: UPSERT `master-design-plan.md` §1/§4/§8 as usual.
8. **Human review.** Each terminal `get_run` carries a `previewUrl` (and sometimes a `studioUrl`, which you always show as a clickable markdown link). Hand it to the user after the first screen for an early direction check. Do not wait for the whole batch to discover a wrong turn.

Real time budget: 2 to 6 minutes per screen with `claude` as the internal agent (OD documents 5 to 30 minutes as its range). Refinement runs (translation, polish) are much shorter than generation runs.

### Field gotchas

- **A wrong-language `agentMessage` is not a wrong-language artifact.** The internal agent's self-report inherits the orchestrating conversation's language even when the HTML came out right. The FILE is the ground truth: grep it (`lang=`, UI strings), and do not fire a correction run over the message's language.
- **The terminal hint of `get_run` can say "produced no files" and be wrong.** With `artifactCount: 1` and the file on disk, the hint lies. The filesystem is the real check.
- **`get_run.updatedAt` freezes during the internal agent's extended thinking.** Minutes of real silence are not a hang. Real liveness is the timestamp of the last event in `events.jsonl`.
- **Orchestrating subagents: foreground loops only.** A subagent that waits on a run with a long background `sleep` pauses itself and stalls the batch. The proven pattern is ONE foreground Bash per run: `for i in $(seq 1 60); do tail -5 "$LOG" | grep -q '"type":"result"' && break; sleep 20; done` (a short `sleep` INSIDE a loop with a timeout is fine; a bare `sleep` is blocked). If you brief a fleet of design agents, put this rule in the briefing explicitly.

**README drift.** The README advertises `od mcp install <agent>` to auto-register in claude/codex/cursor and others. That subcommand did not exist in the release this path was verified against, and registration is manual as above. Check `od --help` before citing it.

## Install your design system as a user package (repo → OD)

Path C originally flows OD → repo (iterate there, convert here). The reverse flow exists too, and it is a prerequisite when the repo ALREADY has a frozen `DESIGN.md` (the UI fidelity contract, Critical Rule 14): before generating anything in Open Design, mirror the project's design system as a user package so every generation inherits the real tokens instead of inventing a palette.

**Format.** The same contract as the bundled ones: `manifest.json` + `DESIGN.md` (Google Labs, same as the repo's) + `tokens.css`, optionally `USAGE.md`. The contracts are in `<bundle>/Contents/Resources/open-design/design-systems/_schema/` (read the `AGENTS.md` there).

**Location** (undocumented, verified in the daemon code: `USER_DESIGN_SYSTEMS_DIR = join(RUNTIME_DATA_DIR, "design-systems")`):

```
~/Library/Application Support/Open Design/namespaces/release-stable/data/design-systems/<slug>/
  manifest.json    # schemaVersion "od-design-system-project/v1", source.type "local"
  DESIGN.md        # verbatim copy of the repo's contract + a provenance header
  tokens.css       # compiled from the live implementation (globals.css), NOT re-chosen
  USAGE.md         # optional: read order + rules for the generating agent
```

Procedure:

1. **Drift check first.** Diff the repo `DESIGN.md` tokens against the live implementation (`app/globals.css` or equivalent). If they diverge, stop and report before mirroring. Watch for formatting false positives (`0.1` vs `0.10`).
2. **tokens.css.** OD's schema is about 57 slots aimed at a marketing page (`--bg/--surface/--fg/--muted`, `--space-1..12` up to 48px, 3 semantic ones). A dense app's design system does not fit: bind each slot BY ROLE to the repo's real value, and re-export the full native vocabulary (ramps, signal palette, and so on) as C-extensions, which the schema explicitly allows. Slots the repo has no spec for get authored and marked `[authored]` at low confidence.
3. **manifest.json.** `source: {"type": "local", "path": "<repo>", "importedAt": "<date>"}`.
4. **Publish.** User packages show up as `status: "draft"` and projects cannot use them (`400 DESIGN_SYSTEM_NOT_PUBLISHED`). There is no obvious UI for this, so use the API:

```bash
# the catalog rescans on every request, no restart; the id carries the "user:" prefix
curl -X PATCH "$DAEMON_URL/api/design-systems/user%3A<slug>" \
  -H "Content-Type: application/json" -d '{"status":"published"}'
```

5. **Smoke test.** `create_project` (MCP) with `designSystem: "user:<slug>"` must return the project with that `designSystemId`. Delete the test project afterwards.

In `USAGE.md`, tell the generating agent to prefer the native token names: an artifact that uses `--bg-2` / `--pass-bg` (or whatever the repo has) ports back without a renaming pass.

## User iteration (in the UI)

On first launch `app-config.json` keeps `onboardingCompleted: false` until the user finishes the wizard in the GUI. That includes the privacy decision and choosing the model engine, so it cannot be automated: it is the user's action.

After that, guide them through these steps:

1. **Create new project**: name + local workspace.
2. **Pick a skill** from the catalog: `frontend-design` for application screens; `list_skills` gives the rest of the catalog. It tells the engine what kind of output you want.
3. **Pick a design system** (from the bundled catalog, the same origin as `getdesign`). The palette can be previewed before committing.
4. **Provide a brief**: product context (industry, tone, target persona, competitor references). If there is a PRD, suggest copying its executive summary. For screen mockups, the `BRIEF.md` goes here.
5. **Iterate.** The engine is BYOK. It auto-detects coding-agent CLIs on the PATH (claude, codex, cursor-agent, opencode, devin, and others) and proxies messages to them by spawning a child process. If it detects none, the user enters an API key for any OpenAI-compatible endpoint in Settings → BYOK. The paid alternative is Open Design Cloud.

Tell them plainly, in their language: "Iterate as much as you like in the UI. When you are happy with the visual direction, come back here and let me know." Do not watch over their shoulder: free exploration is the value of this path.

### Waiting for a person

Path C needs a human by design: onboarding, the privacy choice and the visual iteration are theirs. The decision protocol is `agentic-dev-core/references/decision-protocol.md`.

- **A person is present:** guide the steps above and wait until they say they are done.
- **A supervised worker:** the conductor or launcher relays the instructions and holds the gate. Report that you are waiting and stop; do not poll the app.
- **A routine with nobody:** the delegating brief is the approval source when it covers the decision. When it does not, do the reversible work (install check, preflight, `BRIEF.md`), record the pending step in the session, stop before any outward or irreversible action (installing the app, deleting data) and report. Do not wait for an answer that cannot arrive.

## Output collection

Artifacts go to the project dir under the data root, not to the repo:

```
~/Library/Application Support/Open Design/namespaces/release-stable/data/projects/<project>/
  index.html         # main file, full preview
  *.pdf  *.pptx  *.zip  *.png
```

Metadata is in `data/app.sqlite` (tables `projects`, `conversations`, `messages`, `run_devloop_iterations`, ...).

To pull them out without digging through the filesystem: `od export <file> --project <id> --format pdf|image|pptx --out <path>`. It uses the runtime's Chromium and spends no model calls.

**These are NOT `DESIGN.md`.** Open Design does not emit the Google Labs format, it emits HTML/PDF/PPTX/ZIP. That is why this path has a mandatory conversion stage.

## Bridge step to Path E

Once the user confirms they are happy:

1. **Capture the inputs.** The design-system slug chosen in step 3 (visible in project settings, or `app-config.json` → `designSystemId`), and any custom token tweaked during iteration. `od tools directions --label <label> --json` gives you the direction's full spec so you do not guess tokens.
2. **List the artifacts** under the project dir that the user considers final (there can be several iterations, so ask which one is canonical). If the MCP is registered, `get_artifact` brings the entry file plus all its referenced siblings (CSS tokens, JSX modules, assets) in one call, which is cheaper than N `get_file` calls.
3. **Delegate to `references/llm-authored.md`** with this input appended to the standard briefing:

   > "User iterated in Open Design with design-system `<slug>` and produced these artifacts: `<paths>`. Use the design-system base as a starting point, refine with the visual decisions evident in the HTML (extract tokens from `index.html` inline styles or `<style>` blocks)."

4. Path E runs with those inputs as extra context and produces the final `DESIGN.md` at the project root, following the Google Labs spec.

The bridge goes through Path E instead of converting directly because the Google Labs spec (YAML frontmatter + 8 prescribed sections + lint with `@google/design.md`) is strict. The conversion is a synthesis (what from the HTML goes to the frontmatter and what to the prose, which tokens win when the base design system and the user's tweaks clash), not a mechanical parse. Path E already documents that logic, so do not duplicate it here.

## Cleanup

After Path E confirms `DESIGN.md` is generated and `lint` exits 0:

- **Desktop app:** close it (Cmd+Q). The daemon dies with it and frees the sockets. There is no need to uninstall: the projects stay in the data root if the user wants to iterate again in another session. If it was a one-shot and they want a real cleanup, warn them that deleting `~/Library/Application Support/Open Design/` **removes all their projects** and is irreversible. That decision is theirs.
- **Docker:** `cd /tmp/open-design/deploy && docker compose down`. Ask before adding `-v`: that flag deletes the volume with the projects.

## Troubleshooting

| Symptom                                                       | Likely cause                                                           | Fix                                                                                                                |
| ------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `lsof -i:7456` is empty with the desktop app open             | The desktop app uses a dynamic port + Unix sockets; 7456 is Docker only | Read the real URL from `logs/daemon/latest.log`; verify with `/api/health`                                         |
| `curl` to the daemon returns `404` on `/`                     | Normal: the root is served by the web sidecar, not the daemon          | Try `/api/health`; the app opens the UI itself                                                                     |
| `docker compose up` fails with `port already allocated`       | 7456 is taken                                                          | `OD_PORT=7800 docker compose up -d`, open `localhost:7800`                                                         |
| UI says "No coding agent detected"                            | It found no claude / cursor / codex on the PATH                        | Settings → BYOK with any OpenAI-compatible key, or install the missing CLI and reload                              |
| The app will not open and macOS mentions an unidentified developer | Corrupt download or unofficial build                              | Re-verify with `shasum -a 256 -c` and `spctl -a -vvv`. If it does not say `Notarized Developer ID`, do not open it |
| MCP `open-design` connected but the tools fail                | The daemon is not running                                              | Open the app; `od mcp` proxies to the daemon, it does not start it                                                 |
| `od: command not found`, or `od` prints octal                 | No Open Design `od` on the PATH; `/usr/bin/od` is coreutils            | Call `node "$OD_CLI"` with the absolute path to `daemon-cli.mjs`                                                   |
| `create_project` gives `400 DESIGN_SYSTEM_NOT_PUBLISHED`      | A freshly installed user package stays at `status: "draft"`            | `PATCH /api/design-systems/user%3A<slug>` with `{"status":"published"}` (see the repo → OD section)                |
| `data/projects/` is empty after iterating                     | The render did not finish (timeout or the agent CLI died)              | Re-run the brief from the UI; `tail -f logs/daemon/latest.log`; `od diagnostics export` for a support bundle       |
| The final artifact does not match what the user saw           | Stale cache                                                            | Hard reload (Cmd+Shift+R), export again                                                                            |
| Path E produces a `DESIGN.md` that does not look like the iteration | The bridge did not pass the artifacts correctly                  | Check that the delegation includes the exact HTML paths and the slug; re-run with explicit inputs                  |
