# Topologies — One Shape per Repo Activity

> Loaded by: the conductor, at triage, before anything is created.
> The question is never "how many workers". It is **what does this work write**, because that is
> what decides whether a shared checkout is safe.

---

## 1 · The table

| Activity | Topology | Isolation | Why |
|---|---|---|---|
| `sprint-development` batch-sprint (N stories) | **one Orca worktree per worker, one worker per STORY**; stories that share a module or a migration run SEQUENTIALLY, in one worker or in different rounds | own checkout, own branch, own PR, own dev server, own named browser session | it writes code. Two sessions in one checkout collide on the git index even when they never touch the same file, and two dev servers on one checkout fight over the same `.next/` build directory (G38). Merge and staging deploy stay with the conductor (`references/coordinator-playbook.md` §7) |
| bug burn-down (N independent bugs) | one worktree per bug CLUSTER | own checkout per cluster | every fix is code. Cluster first: three bugs with one root cause is ONE worker, not three |
| `product-management` refinement fan-out (N epics or stories) | **fleet in the SAME checkout**, one worker per epic or story | writes go to the tracker; per-worker session sub-scope | it writes no code. The state of record lives in Jira, so a worktree per story is pure cost: setup time, disk, provisioning surface, and N times the dependency install |
| a cross-cutting refactor split by module | one worktree per module, explicit file ownership per worker | the `File ownership` list in each worker brief | two workers on one module produce merge conflicts by construction |
| `project-context` maps, audits, research | **not a fleet**: one-shot subagents | — | these are reads. A subagent returns a map inside the turn and costs nothing to clean up |
| unattended delivery | `/autonomous-delivery` dispatching into worktrees, inside its mode cap | `references/automations.md` §2.6 | the audit discipline of the unattended run is that skill's, not this one's |
| other unattended routines | scheduled automation over an EXISTING workspace | `references/automations.md` | a fresh workspace per run loses the out-of-git state the routine reads |

**The owner's rule of thumb**: if the task touches files another live session is touching, worktree;
if not, the shared checkout. In backlog refinement there is almost never a file conflict; in story
implementation there almost always is.

## 2 · Partitioning a delivery fleet

The partition unit is the **module**, and for anything that changes the database, the **migration
sequence**. The rule has no exception:

> **Never two workers on the same module.** Not in the same round, not in different worktrees, not
> "just for one file".

Consequences the conductor applies at triage:

1. Group the round's stories by module. Two stories in one module are one worker, run one after
   another in that worker's session, or two rounds.
2. A story that genuinely spans two modules is assigned to ONE worker, which then owns both, and
   both are removed from every other group.
3. Respect the dependency edges in `.context/dev-roadmap.md`: a story whose blocker is not merged
   into the integration branch is not in the round, whatever the tracker says.
4. Two stories that each add a migration never run in the same round: the migration number comes
   from the live ledger at apply time, and the conductor applies them in order
   (`references/coordinator-playbook.md` §7).
5. Whole-repo generated files (`.agents/skills/REGISTRY.md`, the `bun run agents:compat` surfaces,
   Supabase types, `api/schemas/`) are regenerated by the **conductor**, once per integration, never
   by a worker.

Detailed batch mechanics live with the skill that owns the WHAT:
`sprint-development/references/fleet-mode.md`.

## 3 · When a worktree, precisely

Create an Orca worktree when ANY of these is true:

- the work commits code, or runs a generator that rewrites tracked files;
- the work needs its own branch and its own PR;
- the work runs a build, a dev server or anything that writes into a shared build directory;
- two live sessions would otherwise share one git index.

Stay in the shared checkout when ALL of these are true:

- the work's output is tracker artifacts, evidence files and session notes;
- the files it writes are partitioned by an ownership list nobody else appears in;
- nothing it runs writes to a shared build directory.

And note what a worktree is NOT: the harness's own worktree feature lives inside the repo, is
invisible to the board and the phone, and has no managed terminal. For a fleet, always the Orca
worktree. Mechanics, the untracked-files gotcha, the multi-session safety rules and the cleanup
checklist: `git-flow-master/references/worktrees.md`.

## 4 · Git rules per topology

### Same checkout (fleet)

- Stage explicit paths. `git add -A` / `git add .` in a shared tree stages another worker's
  half-finished edit and a secret that happened to be lying there.
- Commit with a pathspec so the commit cannot pick up anything outside your ownership list:
  `git commit -F <message-file> -- <path> <path>`.
- **Re-read every file immediately before editing it.** Another worker may have changed a shared
  neighbour since your last read; an edit built on a stale read silently reverts their work.
- On `index.lock`: wait ~5 s and retry. Do not delete the lock file.
- No repo-wide discards, ever (Critical Rule #13). Restore only paths YOU modified in THIS session.
- The conductor regenerates whole-repo generated files, after the round.

### Own worktree

- `git fetch origin` then verify the new worktree's SHA against `origin/<base>`. A base-ref flag
  resolves LOCAL refs, so a worktree can be born behind the remote; this was paid for twice, and the
  fix is the verification, not the merge. Never hide it behind `|| true`.
- Bring the base in with an ADDITIVE merge. Never rebase or amend anything already pushed
  (Critical Rule #5).
- Push YOUR branch only; open the PR the project's git strategy asks for. A protected branch is
  resolved by `git_strategy.policy.direct_push_to_protected`, never by assumption.
- The base branch cannot be checked out in a worktree if the primary checkout holds it. A worker
  "on the base branch" is in reality a session in the primary checkout — and there the worktree-wide
  terminal stop has extra radius, so count terminals before closing anything.
- Integrate, verify, THEN release the worker, THEN run the orphan audit, THEN remove the worktree
  (`references/coordinator-playbook.md` §6); `worker-release` closes the terminal only, so the removal is not optional.

## 5 · Sizing a round

- The worker cap comes from `.agents/project.yaml` → `orchestration.max_workers`, and an explicit
  user instruction overrides it for that run.
- **A round is concurrency.** It is numbered inside the sprint ("Sprint 42, round 2"); never reuse
  "round" for an execution sprint of `.context/dev-roadmap.md`, which is an ordering, not a
  concurrency group.
- The real ceiling is usually not context but the tracker and deploy-platform rate limits, the
  staging environment the conductor deploys to one story at a time, and how many reports one
  conductor can actually process in a turn. The shipped default in `.agents/project.yaml` →
  `orchestration.max_workers` is deliberately small.
- An ad-hoc single-ticket job (a hotfix, one urgent bug) runs as N=1, outside the rounds, and still
  counts against the cap while it is live.
