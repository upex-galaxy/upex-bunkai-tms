# Measured Gotchas

> Loaded by: the conductor, when something behaves strangely — and read once in full before the
> first fleet on a new machine.
> Every row was PAID FOR in a real Orca session and none of it is in any vendor guide. This page
> keeps the behaviour, the symptom and the fix; the date, the repository and the app version each
> row was measured and last verified on live in a dated record (`.context/ADR/ADR-0003-forensic-measurements-ledger.md`,
> the row for this file), by G-id. Re-confirm a row with `orca agent-context --json` after an
> upgrade, and move it to §3 when it stops being true. The G-ids keep the numbers of the sibling
> boilerplate's ledger, gaps included, so a citation stays valid across both repos.

## 1 · Runtime and mailbox

| # | Gotcha | Symptom | Fix |
|---|---|---|---|
| G1 | **An unacknowledged batch replays forever** and hides everything queued behind it. Delivery is FIFO and a bound Run replays the same batch until it is acked | a `check` returns a message you recognize from 20 minutes ago | ack in the SAME command that re-arms the wait: `check --ack <id> --wait --types … --timeout-ms …`. Leave no window in which the ack can be forgotten |
| G2 | **An unacked batch also kills the notice.** The runtime notifies only on empty → non-empty, so once mail is unread it never notifies again | four messages accumulate for hours and the conductor believes the mailbox is quiet | verify every ack (`acknowledged` equals the id requested, pending count drops) and NEVER put it in a compound command whose exit code gets swallowed |
| G3 | **A Run admits exactly ONE actionable waiter**, and an orphaned one blocks the mailbox. A waiter started with a shell `&` holds the slot with nobody listening | `check` returns a failure naming an existing waiter instead of a batch. A quiet mailbox and a blocked one look identical | arm the waiter as a tracked foreground/background TASK, never with `&`. Recover by locating and killing the stale `orchestration check` process, then re-arm |
| G4 | **Every scripted call needs `</dev/null`.** The binary reads stdin when stdin is attached, and inside a loop or a background shell that read never returns | the command hangs with no output, indistinguishable from slow work | `</dev/null` on EVERY subcommand, not just the orchestration ones |
| G5 | **`check --wait` writes keepalive JSON to stderr every 15 s** (`_keepalive`), unrelated to heartbeat messages | a merged stream looks like it is receiving messages that are not there | filter with `jq 'select(._keepalive|not)'` when merging streams |
| G6 | **Do not build a monitor.** The runtime injects the notice itself; a homemade poller competes with it and can null it, and it triggers on ECHOES — the conductor's own messages are visible on the worker's screen, so a grep for a completion token reads them back as a report | a "report" that is actually the conductor's own instruction, or a notice that never fires | no monitor. Wait inside the turn with one waiter |
| G7 | **A reply body can arrive empty on the worker side** | the worker receives a bare `Re:` and asks the same question again | duplicate a substantive reply with `terminal send` and say in the body that you did — but only while it fits in a sentence or two; past that the duplicate is prose through the lossy verb, so write it to a file and send the pointer (G64, hard rule 4) |
| G8 | **`task-create --deps <json_array>` has an undocumented element shape** — strings with ids, or objects? No example anywhere, and the schema's notes are empty | a dependency graph that silently does not constrain anything | do not use `--deps` yet. Order rounds by hand in `roster.md` |
| G9 | **A task reaches `dispatched` only through a real Dispatch.** A manual status update to `dispatched` is rejected | the ledger says `ready` while the worker is clearly working | create the Dispatch with the launch itself: `worker-start … --agent` (native, supervised) moves the task in the same step, and the plain `dispatch` form gives an addressable id without supervision (G48) |
| G10 | **The permission classifier can block the dispatch call itself**, independently of the terminal running fine | the task stays `ready` instead of `dispatched` | **cosmetic, not functional**: the worker already has its full command. Do not retry around the block; note the gap, continue, and square the ledger with a task status update when the worker finishes |
| G46 | **`orchestration send --to <terminal handle>` never reaches a busy agent.** It queues mail nothing tells the worker to read, and **both it and `terminal send` return `ok: true`**, so the useless call is indistinguishable from the useful one | the worker works on, oblivious; the conductor believes it delivered | the only verb that reaches a RUNNING session is `terminal send`. Mailbox addresses (`run:<id>`, `dispatch:<id>`) are for messages a worker will `check`, never for a nudge |
| G47 | **`dispatch-show --preamble` prints NOTHING under `--json`.** The preamble is text-only output; the JSON form returns the dispatch object without it | a playbook scripted with `--json` everywhere silently delivers an empty preamble | drop `--json` for this ONE call, write the text to a file in the conductor's scope, then point the worker at the file |
| G48 | **`dispatch` WITHOUT `--inject` still creates a dispatch row** (`status: dispatched`, a real addressable id). The vendor grammar documents only the `--inject` case, so a reader cannot tell | a conductor believes it has no dispatch id to address and falls back to screen-scraping | use the plain form on the unsupervised path and keep the id: it is what `dispatch:<id>` and the worker's `worker_done` route on |
| G49 | **`task-create --task-title` and `--display-name` both persist, but the JSON keys are snake_case** (`task_title`, `display_name`), so a read of `.title` returns null and looks like a discarded flag. Omitted, the runtime derives `task_title` from the spec's first line and `display_name` defaults to it, so every dispatched-worker row reads `/<workflow-skill> <label> fleet worker. Read /Users/…` | a task listing and the worker rows in the app are unreadable, and a conductor concludes the flags do nothing | always pass `--display-name "<label>"` (the roster label) and read it back as `.display_name`; `--task-title` is optional. An earlier version of this row said the title flag was discarded: that was a wrong field name in the read, not runtime behaviour |
| G51 | **A realistic wait cannot stay inside the turn.** The harness caps a foreground command at 600 s, while a round runs tens of minutes | a `check --wait --timeout-ms 1800000` is killed mid-wait and the conductor cannot tell a timeout from a dead mailbox | roll the wait: `--timeout-ms 540000`, re-armed with the verified ack in the SAME command, as many times as the round needs. A longer single wait is a background job only when the harness tracks it; the runtime's own mailbox notice stays the primary wake-up |
| G53 | **`escalation` is rejected on the unsupervised path.** A terminal whose `--from` handle owns no supervised dispatch gets `Rejected escalation:` returned as a `status` message, not as an error the worker can act on | a worker reports a hard blocker and nothing arrives; it reads its own rejection as a reply | on that path the brief tells workers to send blockers as `--type status` with the subject prefixed `BLOCKED:`. `escalation` is for supervised workers |
| G56 | **`run-current` returns a null Run for a dispatched worker.** Being dispatched does NOT bind your terminal to the dispatching Run | a worker concludes it is unbound and either guesses a Run from a listing or refuses to create its own | correct and useful: a worker that is ALSO a conductor creates its own Run with no collision, and its upstream reporting still routes, because `worker_done` routes by Dispatch and not by the bound Run. This is what makes a nested conductor legal |
| G57 | **The first `worker_done` revokes the Dispatch, and everything addressed to it afterwards bounces.** `capability_revoked_at` is stamped at that moment | a question the worker raised BEFORE finishing can no longer be answered (`reply` returns `dispatch_inactive`, code and message, not a warning), and a second `worker_done` comes back as `Rejected worker_done: … capability is revoked` even though the worker kept working and produced real output | answer a worker's questions BEFORE it settles, and read a settled worker's later output from its report and its screen, never from the mailbox. A worker that keeps working after `worker_done` is not misbehaving; it has simply lost its channel |
| G59 | **`ask` times out returning EXIT 0.** After its timeout it prints `ask timeout after <ms>ms (thread <id>)` on stdout and exits zero | a worker that branches on `$?` concludes it was answered and proceeds as if the conductor had replied; here it decided a scope question alone | never read `ask` success from the exit code: grep stdout for `ask timeout` and treat that as unanswered. Decide the fallback IN THE BRIEF, before dispatch, so an unanswered `ask` resolves to a stated default instead of the worker's judgement |
| G66 | **The mailbox does NOT truncate; `terminal send` does — same fleet, same day, measured both ways.** The two channels have opposite integrity, and nothing in either receipt says so | a session that meets one mangled `terminal send` concludes "messaging between agents is unreliable" and starts avoiding BOTH channels, when only one is lossy. The good channel is abandoned on the bad one's evidence | assign the channel instead of choosing it (hard rule 4): `orchestration send` for every message between sessions, a file plus a one-line pointer for anything longer than a couple of sentences, `terminal send` only to DRIVE a terminal. Canon: `references/channel-discipline.md` |
| G67 | **An `orchestration send` receipt can carry `"delivered_at": null, "read": 0` in the same payload that proves the message was accepted.** Acceptance and delivery are different facts, reported side by side, and the eye stops at the first one | the conductor reads the success envelope, treats the message as received, and never checks the mailbox row again. The two null fields sitting right there are the evidence it was not read | read the whole receipt, not its status: `delivered_at` and `read` are the delivery facts. Then verify at the DESTINATION anyway (hard rule 17) — the worker's screen, the worker's own acknowledgement, or its next message |
| G68 | **A dispatch binds to a HANDLE, so replacing a terminal orphans it silently in both directions — while `task-list` still reads `dispatched`.** The TASK was dispatched once, which is all the ledger records | the worker believes it escalated and the conductor receives nothing; NEITHER side errors. The worker's own log shows `Rejected escalation: … No active Dispatch belongs to this message sender`, and every status read says the fleet is healthy | re-bind after every terminal replacement (relaunch, crash recovery, runtime restart) with a fresh `dispatch` to the NEW handle. Safe to attempt across the whole roster: it succeeds for a replaced terminal and errors for an unchanged one, so the errors ARE the diagnosis. Never health-check the channel with `task-list`; check the roster's handle column against a live terminal listing |
| G77 | **A dispatched worker cannot start a supervised worker of its own when the app's "Nested worker depth" setting is 1.** `worker-start` from a depth-1 worker returns `nested_worker_depth_exceeded` ("Sub-worker dispatch is not permitted at depth 2 (max 1)"), `effectsApplied: false`; a new Run does not reset the depth | a conductor-of-conductors design (a dispatched super-conductor that launches a sprint conductor, which launches story workers) dead-ends: every conductor below the top has no fleet | probe the depth BEFORE a nested design (one throwaway `worker-start` from the would-be middle layer). At max 1, launch every session that must run its own fleet as a TOP-LEVEL agent (`agent launch`, unsupervised, so depth 0) and route its reports to the upper Run's inbox by `orchestration send --to run:<id>`; the setting is the owner's (Settings, Orchestration) and a worker never changes it |
| G78 | **`worker-start --json` names the dispatch, not the terminal.** The receipt carries the Task and the Dispatch; the terminal handle is in `worker-list` as `agentTerminalHandle` (and `resource.terminalHandle`). `agent launch --json` (unsupervised) is the reverse: `outcome.handle` and no `launch.requested`/`effective` block, so its model is proven only on the rendered screen or the process argv | a conductor reads a null handle from the receipt and cannot nudge or read the worker's terminal; a model claim is made from requested arguments | after `worker-start`, read the handle from `worker-list`; after `agent launch`, verify the model on the screen before claiming it |

## 2 · Terminals, worktrees and launch

| # | Gotcha | Symptom | Fix |
|---|---|---|---|
| G11 | **`terminal create --command` succeeds when the text is DELIVERED, not when it runs.** A line that dies in the shell (quoting error, missing script) reports success and leaves a bare prompt that looks launched | "the fleet is up" and nobody is working | read the screen (`terminal read --screen`) before telling the user the fleet is up, and look for the AGENT's status footer (model, effort, session name), not merely some output |
| G12 | **Recovering a failed launch needs no new terminal.** The tab, the title and the dispatch binding all survive a shell-level failure | recreating the terminal orphans the dispatch rows that point at the old handles | `terminal send --terminal <handle> --text '<corrected line>' --enter` |
| G13 | **`terminal read` needs `--screen` for a repainting TUI.** The default returns accumulated output with escapes stripped | a `clear` typed key by key reads back as `cclclecleaclear`, and spaces a prompt drew by moving the cursor are simply absent | `--screen` returns the rendered frame. The result reports `source`: `stream`, `screen`, or `screen-unavailable` |
| G14 | **The text arrives in `result.terminal.tail`**, an array of lines — NOT `result.lines` | a parser looking for `lines` returns empty forever, silently | read `tail`; siblings are `oldestCursor`, `nextCursor`, `latestCursor`, `returnedLineCount`, `source`, `status` |
| G15 | **The TUI status bar uses non-breaking spaces** | a grep that includes a space after a label never matches | grep the bare token, never a label plus space |
| G16 | **`--screen` and `--cursor` are mutually exclusive** — a screen read is the current frame and has no history to page | an error instead of a read | incremental reads = default stream mode + `--cursor <nextCursor>` |
| G17 | **`tui-idle` is a READINESS signal, not completion.** It means the TUI stopped repainting, which happens the moment the session is ready for input | treating it as "worker finished" reports every ticket complete seconds after launch | completion is `worker_done`, plus the workflow's own artifacts |
| G18 | **`terminal stop` has worktree radius** — it stops the terminals of a whole worktree | a stop meant for one worker kills sibling sessions in the same checkout. Nearly killed three unrelated sessions in another repo | count first; to close ONE, `terminal close --terminal <handle> --tab` |
| G19 | **A context-only injection leaves the worker UNSUPERVISED on purpose**: no dispatch row, so the stop / release / abandon verbs do not close it, and it is reported as unsupervised | cleanup falls back to the worktree-wide stop, with its extra radius | supervision comes from the NATIVE launch (`worker-start … --agent`), not from adopting a terminal — adoption of a custom-argv terminal is refused outright (G44). A terminal you launched yourself is closed by handle, by hand |
| G20 | **A base-ref flag resolves LOCAL refs.** A worktree can be born behind the remote base | the worker builds on a stale base and its merge looks like someone else's regression | `fetch`, then verify the SHA against `origin/<base>`. Never `\|\| true` |
| G21 | **A worktree created early is born stale.** With a moving base, a worktree made half an hour before launch starts behind | same as G20, but with nobody to blame | create the worktree JUST before launching |
| G22 | **Handles change if the runtime restarts**; the sessions survive as separate processes | every handle in the roster is dead while every worker is alive | re-discover with `terminal list --worktree <sel>` and update the roster |
| G23 | **`result.terminal.status == exited` is usually the conductor** having closed that terminal itself | a false "the worker crashed" | correlate with the release you performed before concluding anything |
| G24 | **The setup-hook setting is UI-only.** The CLI does not expose it and desktop automation is blocked by OS permissions on macOS | an automation plan that assumes it can be scripted | the committed `orca.yaml` (`scripts.setup` / `scripts.archive`) is the shared, versioned form and needs no UI; the app field stays a per-machine fallback. `references/orca-machine-setup.md` §4 |
| G25 | **The gate flag is NESTED** (`.result.runtime.reachable`), not a flat field | fails closed and silently on a perfectly capable machine | read the nested path, and test any gate edit by running BOTH branches |
| G26 | **Runs from other repos coexist on one machine** | a conductor that picks a Run from a listing binds to another repo's fleet | never guess: the Run id lives in `run.md`; `run-current` says what this terminal is bound to |
| G44 | **A custom-argv terminal can NEVER be supervised.** The runtime decides "is this an agent" from the argv IT launched, never from the running process, so `worker-start --terminal <handle>` answers `agent_unconfigured` on a terminal whose agent TUI is demonstrably alive on screen | the adoption step fails on a perfectly healthy worker, and the whole fleet runs unsupervised without anyone deciding that | supervision requires the NATIVE path (`worker-start … --agent`). A terminal created with our own command line is unsupervised BY CONSTRUCTION: plan its cleanup by handle and its blockers as `status` (G53) |
| G45 | **A supervised worker gets credentials only from processes that load their own config, and nothing reports a credential gap.** No harness process holds a `.env` value, however it was launched (ADR-0016), so a supervised worker and a pasted launch line start from the same place. On every host each MCP server that needs `.env` values starts through the `.env` loader (`varlock run --filter <its vars>`), which reads the checkout's `.env` at spawn time. Nothing exports `.env` into the worker's shell (Critical Rule #1): the CLIs carry their own auth (`acli`, `gh`, `supabase`, `vercel`), bun scripts load `.env` themselves, and any other command that needs a value runs as `bunx varlock run -- sh -c '<cmd using "$VAR">'` | a worktree with no `.env` (never provisioned), a session not restarted after a `.env` change, or a CLI never logged in on this machine: the worker launches fine and fails much later, at its first authenticated probe, with an error that reads like a broken tool | provision the worktree (`bun run worktree:provision`), restart the session after a `.env` change, log in the CLIs a brief calls (`references/orca-machine-setup.md` §3.2); VERIFY credentials on the worker's screen before dispatching work (an MCP server listed as connected, or the worker's own first probe) |
| G50 | **The board card has no per-worker shape in a same-checkout fleet.** `worktree set --comment` is per-WORKTREE, and the manual-QA topology is N workers in ONE checkout | the playbook's per-worker recovery block (session label, branch, brief path) cannot be expressed, and a conductor either overwrites it N times or skips the card | ONE fleet-level card per worktree; per-worker recovery lives in `roster.md`, which the card points at by absolute path. Shape: `references/coordinator-playbook.md` §3 |
| G52 | **`terminal send` can answer `agent_prompt_stalled` and still have queued the text.** Sent while the agent is mid-turn, the call reports the stall AND the text becomes the session's next prompt | the retry delivers the message twice, and the worker acts on it twice | on `agent_prompt_stalled`, read `worktree ps` (or the screen) to see whether the text is already the pending prompt BEFORE resending. Usually there is nothing to resend |
| G55 | **Idle and stalled are indistinguishable from the prompt line.** The prompt box is ALWAYS drawn, so a screen read that greps for the prompt character reports "idle" for every worker, always — including one that is working | a naive sweep says the whole fleet is idle, or says a stalled worker is fine | the signal is the SPINNER line above the prompt box (`✽ …ing… (Nm Ns · ↓ N tokens)`): no spinner and no `worker_done` = **stalled**, no spinner after `worker_done` = **idle**. Corroborate with the worker's own progress timestamp before concluding |
| G58 | **The injected task spec IS the worker's first prompt; the brief arrives second.** `worker-start` hands the spec to the agent immediately, so the worker begins executing before any later `terminal send` lands | the worker runs on the spec's one-line framing for its first stages and only reconciles when the brief shows up. Measured cost: three commits carried the harness-derived session label instead of the fleet label, unfixable once pushed (Critical Rule #5) | the spec must be self-sufficient: the brief's absolute path, the continuation sentence, AND anything that must be right from the first action (the session label, the no-stopping clause). Write the brief BEFORE `task-create` so the spec can cite it |
| G60 | **`terminal send` silently truncates a long payload and still reports `accepted: true` with a byte count.** A 2399-byte instruction arrived as its last fragment only | the conductor believes a multi-point instruction was delivered; the worker acts on the surviving fragment and asks for the rest, or worse, guesses | same rule as the brief: anything longer than a couple of sentences goes in a FILE and the terminal gets a one-line pointer with the absolute path. The reported `bytesWritten` counts what was WRITTEN, not what the agent received |
| G61 | **`terminal send --interrupt` does not clear a Claude TUI input box.** The call is accepted (1 byte) and the pre-typed text is still on screen afterwards | the next `--text … --enter` is PREPENDED by whatever a human or an earlier session left typed, and the combined line is submitted as one prompt | read the screen before sending into a terminal you did not just create. If text is pending, absorb it: open your message by naming that leading fragment and saying what to do with it, rather than assuming it will be discarded |
| G62 | **The embedded browser refuses `navigator.clipboard.readText()`, and bringing the tab to the foreground does not fix it.** `NotAllowedError: … Document is not focused.` | the obvious design for getting a rendered page's result back — the human presses Copy, the agent reads the clipboard — cannot work, and it fails at the last step, after the page and the tab both worked | serve the page over loopback and let its own submit return the result to the agent; the clipboard is not a channel here. A read-only page needs no channel at all and a `file://` URL is enough. Details: `references/html-surfaces.md` |
| G64 | **What survives a truncated `terminal send` is the TAIL, so the damage does not look like a truncation.** G60's mechanism seen from the receiving end: the head is what gets lost | the recipient gets a fragment that starts mid-word — measured verbatim: `"l y read 0 en el mismo payload."` and, in the other direction, `"e es bidireccional y frecuente, no anecdotico. Dato duro que ayuda a diagnosticar: …"`. It reads like a typo, a stray keystroke or a paste accident, NOT like a missing message, so nobody goes looking for the rest and the receiving session answers the fragment. Had the tail been lost instead, it would at least read as cut off | the sender's fix is G60's (a file plus a one-line pointer); the reader's fix is new and is hard rule 19: **a message that begins mid-sentence is a truncation until proven otherwise.** Quote what arrived, ask for the pointer, never answer the fragment |
| G65 | **`terminal send` answering `ok: false` is the runtime protecting a HUMAN who is typing in that terminal**, not an error to retry | indistinguishable from a transport failure if you read only the boolean — and the retry interleaves your keystrokes with theirs in the same input box, or worse, a "safer" longer message goes out and truncates | read it as "a human is driving this terminal, wait". Do not retry, do not fall back to a longer payload, do not conclude the session is unreachable. Re-read the screen before sending again (G61: the box is not cleared by `--interrupt`) |
| G71 | **`worker-start` titles every worker tab `worker-<task id>` and has no flag to change it.** The runtime sets that string as the tab's custom label, which outranks the TUI's own title, so the session name a harness paints never shows on the tab | the owner opens a fleet and every tab reads `worker-task_…`: the id is there, what the worker is doing is not | rename the tab right after the launch returns its handle: `terminal rename --terminal <h> --title "<label> · <short task id>"` (G72 says when it lands). Neither `--name` nor `--display-name` on `worker-start` helps: both name a NEW worktree |
| G72 | **`terminal rename` writes two places, and `terminal list` / `terminal show` read the wrong one.** It sets the runtime title of the pty (what `.title` returns) and asks the app window to set the tab label. On a tab the window has open, the TUI's next title escape overwrites the runtime title while the label keeps the rename; on a tab the window never opened, the label is NOT updated and only the runtime title changes | the same verb looks like a failure on tabs where it worked and like a success on tabs where the owner still sees the old label | never verify a tab label with `terminal list` or `terminal show`: check it on the tab itself (or ask the owner). Rename at launch AND again in every liveness sweep, since a rename is idempotent and a background tab only takes it once the window has opened it |

## 3 · Lies in the vendor guide (verified by hand, not read)

| The guide says | Reality |
|---|---|
| use `check --unread --inject`, recommended twice | **`--inject` does not exist on `check`.** The runtime answers with an unknown-flag error; `--inject` lives only on `dispatch` |
| `coordinator-start` / `coordinator-stop` appear in `--help` with all their flags | **retired**: both are no-ops that return a recovery action and perform no effect. The schema now says so in its own notes |
| `skills get --reference` / `--references` | **rejected.** Valid flags are `--full`, `--json`, `--topic` (plus the global ones) |
| `task-create --deps <json_array>` | the flag exists; the ELEMENT shape is documented nowhere and the schema's notes are empty (G8) |

## 4 · Repo and harness traps that bite a fleet

| # | Gotcha | Symptom | Fix |
|---|---|---|---|
| G27 | **Launching in an edits-only permission mode.** It covers file edits, not COMMANDS, so every script call waits on a human who is not watching | a worker that leaves every tracker mutation computed and unexecuted | launch each tier in the mode `orchestration.permission_modes` declares (worker `bypass` by default), never edits-only. Updated 2026-10-29: the original fix said "an auto permission mode", but Claude Code's `auto` pauses and prompts after 3 consecutive or 20 total classifier blocks, so it is not non-interactive either (`references/orca-machine-setup.md` §3.1, G79) |
| G28 | **An effort flag that does not validate.** An invalid effort level starts the session on the default with nobody told; the permission-mode flag DOES reject an invalid value | a fleet silently running at default effort | pin the full model id and a known effort level, and confirm both in the agent's status footer on screen |
| G29 | **A model alias moves on its own.** An alias means "the latest", so a fleet pinned to an alias changes model under you between rounds | irreproducible results across rounds | pin the FULL provider model id |
| G30 | **A quoting character in the prompt kills the line.** A double quote or an angle bracket inside the prompt breaks the shell parse | five launch lines died at once and the environment variables never exported; the terminals looked fine | no `"` and no `<` / `>` inside the prompt; validate every line with a shell syntax check before launching |
| G31 | **Ten live worktrees took the runtime down twice** in one session | runtime timeouts, a fleet that stops responding | close a finished worker in the SAME turn, not at the end of the round |
| G32 | **Creating the terminal and not sending the brief**, twice in one day | a worker idle for FIVE hours | create + launch + brief is one indivisible operation; verify with a working-tree status check within minutes |
| G33 | **Four tasks in one message** | the worker executed one | one message, one task |
| G34 | **Periodic heartbeats wake the conductor to read "alive"**, and the injected preamble asks for them | the conductor interrupted every few minutes per worker | the brief prohibits them explicitly, with the reason |
| G35 | **The harness's agent-messaging tool does not reach the conductor** from an isolated worktree | five workers once reported this way: two to an unrelated session, three left typed and unsent; the conductor found out by reading screens up to 35 minutes late | the mailbox is the channel; the brief prohibits the alternative |
| G36 | **A user-question prompt from a worker is seen by nobody** | one question waited 7.5 hours | a blocking `ask` to the conductor, or a message plus continuing on what does not depend on it |
| G37 | **Orphaned browser sessions.** Ten headless browsers, ~2.7 GB, running for hours | machine slowdown the owner noticed before the fleet did | close every browser-automation session before reporting, including subagents' |
| G38 | **Two dev servers on one checkout fight over the same build directory.** Splitting PORTS does not help | 404s with missing-file errors from the build cache | one dev server per worktree |
| G39 | **A full disk makes a worker MUTE, not failed.** Writing the output fails, not the command, and the message command is also a shell process; file writes keep working | a worker that works and reports nothing | check free disk before a long round; each worker can leave hundreds of MB of build cache |
| G40 | **A brief that cites an uncommitted path in the conductor's own scope is invisible to a worker in a worktree** | the worker proceeds without its context, silently | cite ABSOLUTE paths into the primary checkout |
| G41 | **A skill can exist only in the primary checkout** (gitignored T3 install) | `Unknown skill` in the worktree | provision it (`references/provisioning.md`); verify with `git check-ignore` before assuming it travels |
| G42 | **A declared MCP server is not an enabled one.** A server disabled for the project leaves the session without tools AND without an error | a worker that quietly skips the database or API leg of its exploration | the worker's domain skill keeps its own non-bypassable tool probe; never route that probe through the orchestrator |
| G43 | **A git index collision in a same-checkout fleet**, even between workers editing disjoint files | a failed commit, or a commit that picked up a sibling's staged file | stage explicit paths, commit with a pathspec, retry on `index.lock` |
| G54 | **A worker's cost exists only on its own screen, and closing the terminal destroys it.** No command reports a session's tokens or context use; the agent's own footer does | the fleet's cost accounting is missing exactly the workers that were closed correctly and promptly | read the footer (`terminal read --screen`) as part of the CLOSE ritual, before releasing or closing anything, and write the numbers into `roster.md`. The conductor's own usage is not readable from inside its session at all |
| G63 | **`git:policy verify` reports host DRIFT when the active `gh` account simply cannot SEE the ruleset's bypass list.** A non-privileged reader gets `bypass_actors: null` and `current_user_can_bypass: "never"` from the same unchanged ruleset | the report says `admin_bypass declared: true / enforced: false` and exits 1. ## 5 · Two laws worth more than any single row

1. **An exclusion declared by SELECTOR only excludes where someone already looked; one declared by
   MECHANISM excludes where nobody has looked yet.** Three separate incidents shared this shape (a
   forbidden trailer matched by exact string instead of by rule, a contrast check that stopped at the
   first background image, a rename sweep that missed prose). Prefer the mechanism.

2. **Beware a tool whose radius exceeds the intention.** The worktree-wide terminal stop, a repo-wide
   git discard, an untargeted stash: each does more than the sentence that called it. Count, scope,
   or pick the narrower verb.
