# Business feature map generator

> **Purpose**: Generate or update the map of `business-feature-context`, an inventory of every feature in the system, so developers can plan implementation, extension and refactor work against one source of truth.
> **Output**: `.agents/skills/business-feature-context/references/business-feature-map.html` (the placeholder the skill ships with is replaced on CREATE). Anatomy, section contract and incremental update: `../../agentic-dev-core/references/business-context-maps.md` §2 and §4; this reference says what goes in the sections.

**Target**: `$ARGUMENTS` forwarded by the alias or given in the invocation (module filter, domain name, or blank for the full system)

---

## What this produces

One HTML map that catalogs every feature of the system with:

- Feature identification, status and maturity (Stable / Beta / Planned / WIP / Deprecated)
- A CRUD matrix per entity (which operations are implemented end to end)
- The API endpoint inventory, grouped by domain
- The UI component and page inventory (forms, dashboards, modals)
- Third-party integrations (payments, email, auth, analytics, storage)
- Feature flags and WIP signals (env vars, TODOs, stub handlers, recent branches)
- Discovery gaps (suspected features without confirmation, deprecated code paths)

It is the feature-centric complement to the data map in `business-data-context` (entities, RLS, flows, ownership) and the API map in `business-api-context` (route groups, auth, error shapes). Together they let `/project-context master-plan` and `/sprint-development` reason about scope without re-reading the codebase, each read through `bun run context:map <skill>`.

---

## Line-1 banner

The generated map begins with `<!-- generated by project-context mode features; edited in place by business-feature-context refresh; do not hand-edit -->`. The reader, the updater and the doctor use it to tell the map from the placeholder (`business-context-maps.md` §2). The `<h1>` carries the project name, and the `overview` section names the sources (API routes, frontend pages, DB schema, backend services, feature flags, recent git log) and the companion maps.

## Sources (use all available)

Exhaust every source and cross-reference code with the DB, the API and existing docs, because code alone hides flags, integrations and planned work. App paths resolve under `{{stack.app_root}}` (SKILL.md § Stack parameters).

| Source                   | What to extract                                                             | Tool                                                                                               |
| ------------------------ | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| API routes / endpoints   | Features exposed via HTTP: each endpoint is a developer-visible capability | Read route files; if OpenAPI exists, parse `api/openapi.json`; use `[API_TOOL]` if available. Supabase-direct app: the client calls (`api.md` § Supabase-direct API) |
| Frontend routes + pages  | User-facing features: each page, form or modal is a user operation          | Read `{{FRONTEND_REPO}}/{{FRONTEND_ENTRY}}`, focusing on routes, pages, forms, modals, dashboards  |
| Database schema          | Entities that back features: CRUD capabilities per entity                   | per `{{stack.database.schema_source}}`: `[DB_TOOL]` (Supabase MCP) read-only queries for table structure and FK relationships, or the migration files under `{{stack.database.migrations_dir}}` |
| Backend services         | Business logic, validation, processing, background jobs                     | Read `{{BACKEND_REPO}}/{{BACKEND_ENTRY}}`, focusing on services, controllers, handlers, workers    |
| Package dependencies     | Third-party integrations (payments, email, auth, analytics, monitoring)     | Read `package.json`, `requirements.txt`, `Gemfile`, etc.                                           |
| Feature flags / env vars | Disabled, experimental or beta features                                     | Grep for `FEATURE_`, `ENABLE_`, `BETA_`, `isEnabled`, `feature.*flag` in codebase + `.env.example` |
| Existing context         | PRD, SRS, the data map, domain glossary                                     | `.context/PRD/`, `.context/SRS/`, `bun run context:map business-data-context`                     |
| Legacy map (input only)  | a project's old markdown feature map                                        | `.context/business/business-feature-map.md` when present: read it as input and cite it in `data-migrated-from`; it stays on disk, unedited |
| Design context           | which screen implements which story                                         | the master design plan's US→Screen map (`/design-system`), when it exists                          |
| Git history (recent)     | Recently added, in-progress or deprecated features                          | `git log --oneline -30` plus `git branch -a` for active feature branches                           |

The test for a feature is whether the system offers a capability: API endpoints, UI actions, background processes and integrations all count. If a user or the system can do it, it is a feature.

## Workflow

### Step 1: Identify scope

- Read `$ARGUMENTS`:
  - Empty: scan the full system.
  - A module or domain name (for example `billing`, `auth`): scope the reads to that domain.
  - A path (for example `apps/api/src/billing/`): restrict file reads to that subtree.
- Report the scope back to the user before the heavy work starts.

### Step 2: Read API routes

- Find the API entrypoint(s): Next.js `app/api/`, Express or Fastify route registration, NestJS controllers, and so on.
- For each endpoint extract `METHOD path | auth-required? | handler file | brief purpose`.
- If `api/openapi.json` exists, prefer it (faster, canonical) and use raw code only to fill gaps.
- Group endpoints by domain (auth, billing, users, products and so on).
- A Supabase-direct app has no route handlers for some domains. Its capabilities are the Supabase client calls in the app code (`.from(<table>)`, `.rpc(<function>)`, `auth`, `storage`, `functions.invoke`). Record them as `Client | <table or function> | operation | calling file`.

### Step 3: Map frontend pages

For each page, form, modal or dashboard found, answer:

- What user action does it enable?
- What data does it display or collect?
- Which API endpoints does it call? (grep for fetch, axios or api-client usage in the page tree)
- Which user roles can reach it? (look for middleware, route guards, RLS hints)

### Step 4: Cross-check with the DB schema and backend services

- Read the DB schema from the source `{{stack.database.schema_source}}` names: `[DB_TOOL]` (Supabase MCP) to list tables, columns and FK relationships, or the migration files in order.
- Read the backend services and handlers in scope.
- Build the CRUD matrix: for each entity, mark which of the C/R/U/D operations have an API endpoint, a UI affordance and a backend service or handler.
- Flag entities with partial CRUD (read-only, soft-delete only and the like), which are common gaps.

### Step 5: Grep for feature flags and env vars

- Grep the codebase for `FEATURE_`, `ENABLE_`, `BETA_`, `isEnabled(`, `feature.*flag`, `flags\.`.
- Read `.env.example` (and `.env.staging.example` or `.env.production.example` if present) for documented flags.
- For each flag note its name, default value, where it is read and what it gates.

### Step 6: Read recent git history

```bash
git log --oneline -30
git branch -a --sort=-committerdate | head -20
```

It shows features added in the last two weeks or so (probably still Beta), active feature branches not yet merged (WIP) and recent reverts or deprecations (Deprecated).

### Step 7: Cross-link with the data map (soft gate)

If `bun run context:map business-data-context` prints a generated map:

- Every entity in the data map should have CRUD coverage in this map, or be flagged as read-only or system-owned.
- Every business flow in the data map should map to at least one feature.
- Flag mismatches in the `discovery-gaps` section and keep going.

If it prints a placeholder notice (no data map yet):

- Continue without it.
- Note in the `overview` section: Companion data map not generated yet, cross-checks skipped.
- Suggest the user run `/project-context data` afterwards for full coverage.

### Step 8: Write output

Before drawing the first figure, run the point-of-use check for capability `diagrams` (`../../agentic-dev-core/references/business-context-maps.md` §7). Then write `.agents/skills/business-feature-context/references/business-feature-map.html` using the Output structure below.

In UPDATE mode:

1. Generate the stale sections only, in memory.
2. Show a section-level diff (sections regenerated and untouched, features added and removed, status changes).
3. Ask the user to confirm before writing, because an auto-overwrite loses hand-made edits. With nobody to ask, SKILL.md "With nobody at the keyboard" says who approves.

After writing, `bun run context:map business-feature-context --list` prints every section with the run's date and no placeholder notice. Then review the skill's rules and `references/gotchas.md` against the new map. A rule the map contradicts is proposed for "No longer true" and is not deleted.

### Step 9: Report gaps

Close with a Discovery gaps section and a brief CLI report that gives:

- Total features by status
- CRUD coverage summary
- Integrations count
- Number of WIP and Beta features
- The top three discovery gaps that need team clarification

## Output structure

Write the map as flat `<section>`s in this order, each with the stable `id` named in its heading below, its `data-sources` and its `data-updated` date. The markdown snippets show the columns; render them as HTML tables. A figure (diagram-design) goes where a picture carries the mechanism: one overview figure for the module landscape, a flowchart for a flow that crosses several features. Every fact a figure shows is also in the section text.

### 1. `overview`: inventory summary

```markdown
| Category   | Features | Status         |
| ---------- | -------- | -------------- |
| Core       | [count]  | Stable         |
| Secondary  | [count]  | Stable         |
| Beta       | [count]  | Testing        |
| Planned    | [count]  | In Development |
| Deprecated | [count]  | Being removed  |
```

### 2. `module-<slug>`: feature catalog (by domain)

One section per domain, each feature an `<h3>` inside it:

```markdown
#### Feature: [Name]

| Aspect           | Value                                |
| ---------------- | ------------------------------------ |
| **ID**           | FEAT-NNN                             |
| **Status**       | Stable / Beta / Planned / Deprecated |
| **Endpoints**    | [list of METHOD path]                |
| **UI**           | [components/pages/routes]            |
| **Owners**       | [roles / actors who use it]          |
| **Dependencies** | [services, integrations]             |
| **Evidence**     | [code path(s)]                       |
| **GUARD folder** | `src/features/<name>/` or `none`     |
| **Proven by**    | [test or live check] or `none yet`   |

**Capabilities:**

- [x] Implemented capability
- [ ] Missing or planned capability
```

`GUARD folder` names the feature's folder under the GUARD layout (`agentic-dev-core/references/guard-architecture.md`), and the feature keeps that name. `Proven by` names the unit test, QA ATC or live check that shows the feature works; `none yet` is a gap that Step 9 reports.

### 3. `crud-matrix`: CRUD matrix

```markdown
| Entity | Create | Read | Update | Delete  | Evidence   |
| ------ | ------ | ---- | ------ | ------- | ---------- |
| User   | ✅     | ✅   | ✅     | ⚠️ Soft | api/users/ |
```

Legend: ✅ Full, ⚠️ Partial/conditional, ❌ Not available

### 4. `route-inventory`: API endpoint inventory

Grouped by domain. Columns: `Method | Endpoint | Purpose | Auth | Handler file`. The meaning of each route group (auth model, error semantics, journeys) belongs to the API map, so cite its section ids and do not restate them.

### 5. `ui-inventory`: UI component inventory

Three sub-tables:

- Forms: `Page route | Form name | Submits to (endpoint) | Validation lib`
- Dashboards / Views: `Page route | View name | Data source endpoint(s) | Role gating`
- Actions: `Component | Type (modal/dialog/confirm) | Trigger | Endpoint called`

### 6. `integrations`: third-party integrations

| Service | Purpose | Package | Status | Features using it |
| ------- | ------- | ------- | ------ | ----------------- |

### 7. `flags-and-wip`: feature flags and WIP

Active flags:

| Flag | Description | Default | Environment | Read by (file) |
| ---- | ----------- | ------- | ----------- | -------------- |

WIP signals (from git and grep):

| Signal                 | Evidence                            | Estimated status |
| ---------------------- | ----------------------------------- | ---------------- |
| `feature/UPEX-XYZ-...` | Active branch, last push N days ago | WIP              |
| `TODO: implement X`    | path:line                           | Planned          |

### 8. `discovery-gaps`: discovery gaps

This section is mandatory. List the features that:

- Could not be verified from code
- Appear partially implemented
- Have unclear ownership or purpose
- Look deprecated but are not formally marked
- Need team clarification before they are scoped

Make each gap actionable: what to ask, whom to ask, or what to grep for next.

---

## Downstream consumers

The map is read through `bun run context:map business-feature-context` by:

- `/project-context master-plan`, which uses the feature catalog and CRUD matrix to scope multi-story epics and find gaps.
- `/project-context api`, which cross-references the endpoint inventory section.
- `/sprint-development` (Planning step), which reads the relevant domain section when scoping a story.

Keep section ids stable so downstream consumers can address them with `--section <id>`.

---

## Rules / constraints

1. Read before you write. In UPDATE mode, read the existing map through `--list` and `--section`, regenerate only the stale sections and diff them. A blind overwrite loses hand-made edits, and a changed section id breaks downstream readers.
2. Surface every deletion. When a feature disappears between runs, show it in the diff and explain why (likely a deprecation or a rename).
3. Code is the ground truth. When the PRD or SRS disagrees with the code, the code wins and the mismatch goes in `discovery-gaps`.
4. Respect scope. When `$ARGUMENTS` restricts scope, scan nothing outside it, and note in the header which domains were skipped.
5. Leave test coverage out. This is a dev-side feature inventory: no test coverage matrices, ATC references or QA-side relevance, which belong to the QA boilerplate's counterpart.
6. Soft gates only. When the data map is still a placeholder, continue and suggest running `/project-context data` next.
