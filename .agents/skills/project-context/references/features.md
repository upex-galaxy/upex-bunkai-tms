
# Business Feature Map Generator

> **Purpose**: Generate or update the map of `business-feature-context`, a comprehensive inventory of every feature in the system, so developers can plan implementation, extension, and refactor work against a single source of truth.
> **Output**: `.agents/skills/business-feature-context/references/business-feature-map.html` (the placeholder the skill ships with is replaced on CREATE). Anatomy, section contract and incremental update: `../../agentic-dev-core/references/business-context-maps.md` §2 and §4; this reference says WHAT goes in the sections.
> **Audience**: Developers planning roadmap, scoping new work, or onboarding to an unfamiliar module.

**Target**: `$ARGUMENTS` forwarded by the alias or given in the invocation (module filter, domain name, or leave blank for full system)

---

## What this produces

One HTML map that catalogs **every feature** of the system with:

- Feature identification, status, and maturity (Stable / Beta / Planned / WIP / Deprecated)
- CRUD matrix per entity (which ops are implemented end-to-end)
- API endpoint inventory grouped by domain
- UI component / page inventory (forms, dashboards, modals)
- Third-party integrations (payments, email, auth, analytics, storage)
- Feature flags + WIP signals (env vars, TODOs, stub handlers, recent branches)
- Discovery gaps (suspected features without confirmation, deprecated code paths)

This is the **feature-centric** complement to:

- the data map in `business-data-context` (data-centric: entities, RLS, flows, ownership)
- the API map in `business-api-context` (API-centric: route groups, auth, error shapes)

Together they let `/project-context master-plan` and `/sprint-development` reason about scope without re-reading the codebase from scratch, each read through `bun run context:map <skill>`.

## Line-1 banner

The generated map MUST begin with `<!-- generated by project-context mode features; edited in place by business-feature-context refresh; do not hand-edit -->` so the reader, the updater and the doctor know it is no longer the placeholder (`business-context-maps.md` §2). The `<h1>` carries the project name; the `overview` section names the sources (API routes, frontend pages, DB schema, backend services, feature flags, recent git log) and the companion maps.

## Sources (use ALL available)

Exhaust every source. Do not rely on code alone — cross-reference with DB, API, and existing docs. App paths resolve under `{{stack.app_root}}` (SKILL.md § Stack parameters).

| Source                   | What to extract                                                             | Tool                                                                                               |
| ------------------------ | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| API routes / endpoints   | Features exposed via HTTP — each endpoint is a developer-visible capability | Read route files; if OpenAPI exists, parse `api/openapi.json`; use `[API_TOOL]` if available. Supabase-direct app: the client calls (`api.md` § Supabase-direct API) |
| Frontend routes + pages  | User-facing features — each page/form/modal is a user operation             | Read `{{FRONTEND_REPO}}/{{FRONTEND_ENTRY}}` — focus on routes, pages, forms, modals, dashboards    |
| Database schema          | Entities that back features — CRUD capabilities per entity                  | per `{{stack.database.schema_source}}`: `[DB_TOOL]` (Supabase MCP) read-only queries for table structure and FK relationships, or the migration files under `{{stack.database.migrations_dir}}` |
| Backend services         | Business logic, validation, processing, background jobs                     | Read `{{BACKEND_REPO}}/{{BACKEND_ENTRY}}` — focus on services, controllers, handlers, workers      |
| Package dependencies     | Third-party integrations (payments, email, auth, analytics, monitoring)     | Read `package.json`, `requirements.txt`, `Gemfile`, etc.                                           |
| Feature flags / env vars | Disabled, experimental, or beta features                                    | Grep for `FEATURE_`, `ENABLE_`, `BETA_`, `isEnabled`, `feature.*flag` in codebase + `.env.example` |
| Existing context         | PRD, SRS, the data map, domain glossary                                     | `.context/PRD/`, `.context/SRS/`, `bun run context:map business-data-context`                     |
| Legacy map (input only)  | a project's old markdown feature map                                        | `.context/business/business-feature-map.md` when present: read as input, cite it in `data-migrated-from`; never delete or rewrite it |
| Design context           | which screen implements which story                                         | the master design plan's US→Screen map (`/design-system`), when it exists                          |
| Git history (recent)     | Recently added, in-progress, or deprecated features                         | `git log --oneline -30` plus `git branch -a` for active feature branches                           |

**Golden rule**: a feature is any **capability the system offers** — API endpoints, UI actions, background processes, integrations. If a user or system can DO it, it's a feature.

## Workflow

### Step 1: Identify scope

- Read `$ARGUMENTS`:
  - If empty → full-system scan
  - If a module/domain name (e.g. `billing`, `auth`) → scope reads to that domain
  - If a path (e.g. `apps/api/src/billing/`) → restrict file reads to that subtree
- Report scope back to the user before doing the heavy lifting.

### Step 2: Read API routes

- Discover the API entrypoint(s): Next.js `app/api/`, Express/Fastify route registration, NestJS controllers, etc.
- For each endpoint extract: `METHOD path | auth-required? | handler file | brief purpose`.
- If `api/openapi.json` exists, prefer it (faster, canonical) and use raw code only to fill gaps.
- Group endpoints by domain (auth, billing, users, products…).
- Supabase-direct app (no route handlers for a domain): its capabilities are the Supabase client calls in the app code (`.from(<table>)`, `.rpc(<function>)`, `auth`, `storage`, `functions.invoke`); record them as `Client | <table or function> | operation | calling file`.

### Step 3: Map frontend pages

For each page, form, modal, dashboard found:

- What user action does it enable?
- What data does it display or collect?
- Which API endpoints does it call? (grep for fetch / axios / api-client usage in the page tree)
- Which user roles can access it? (look for middleware, route guards, RLS hints)

Look for: route segments, form components, modal/dialog components, dashboard widgets, table/list views, primary action buttons.

### Step 4: Cross-check with DB schema and backend services

- Read the DB schema from the source `{{stack.database.schema_source}}` names: `[DB_TOOL]` (Supabase MCP) to list tables, columns, FK relationships, or the migration files in order.
- Read backend services / handlers in scope.
- Build the CRUD matrix: for each entity, mark which of C/R/U/D ops have:
  - An API endpoint
  - A UI affordance
  - A backend service / handler
- Flag entities with partial CRUD (read-only, soft-delete only, etc.) — these are common gaps.

### Step 5: Grep for feature flags and env vars

- Grep the codebase for: `FEATURE_`, `ENABLE_`, `BETA_`, `isEnabled(`, `feature.*flag`, `flags\.`.
- Read `.env.example` (and `.env.staging.example` / `.env.production.example` if present) for documented flags.
- For each flag note: name, default value, where it's read, what it gates.

### Step 6: Read recent git history

```bash
git log --oneline -30
git branch -a --sort=-committerdate | head -20
```

Use this to spot:

- Features added in the last ~2 weeks (likely still warm — may be Beta)
- Active feature branches not yet merged (WIP features)
- Recent reverts or deprecations (Deprecated features)

### Step 7: Cross-link with the data map (soft gate)

If `bun run context:map business-data-context` prints a generated map:

- Every entity in the data map should have CRUD coverage in this map (or be explicitly flagged as read-only / system-owned).
- Every business flow in the data map should map to at least one feature.
- Flag mismatches in the **Discovery gaps** section — do NOT block.

If it prints a placeholder notice (no data map yet):

- Continue without it.
- Note in the `overview` section: Companion data map not generated yet, cross-checks skipped.
- Suggest the user run `/project-context data` afterwards for full coverage.

### Step 8: Write output

Before drawing the first figure, run the point-of-use check for capability `diagrams` (`../../agentic-dev-core/references/business-context-maps.md` §7). Write `.agents/skills/business-feature-context/references/business-feature-map.html` using the **Output structure** below.

In UPDATE mode:

1. Generate the stale sections only, in memory.
2. Show a section-level diff (sections regenerated vs untouched, features added/removed, status changes).
3. Ask the user to confirm before writing. NEVER auto-overwrite.

After writing: `bun run context:map business-feature-context --list` prints every section with the run's date and no placeholder notice. Then review the skill's rules and `references/gotchas.md` against the new map; a rule it contradicts is PROPOSED for "No longer true", never deleted.

### Step 9: Report gaps

Always close with a Discovery gaps section AND a brief CLI report including:

- Total features by status
- CRUD coverage summary
- Integrations count
- Number of WIP / Beta features
- Top 3 discovery gaps that need team clarification

## Output structure

Write the map as flat `<section>`s in this order, each with the stable `id` named in its heading below, its `data-sources` and its `data-updated` date. The markdown snippets show the columns; render them as HTML tables. A figure (diagram-design) goes where a picture carries the mechanism: one overview figure for the module landscape, a flowchart for a flow that crosses several features. Every fact a figure shows is also in the section text.

### 1. `overview`: inventory summary

```markdown
| Category   | Features | Status         |
| ---------- | -------- | -------------- |
| Core       | [count]  | Stable         |
| Secondary  | [count]  | Stable         |
| Beta       | [count]  | Testing        |
| Planned    | [count]  | In Development |
| Deprecated | [count]  | Being removed  |
```

### 2. `module-<slug>`: feature catalog (by domain)

One section per domain, each feature an `<h3>` inside it:

```markdown
#### Feature: [Name]

| Aspect           | Value                                |
| ---------------- | ------------------------------------ |
| **ID**           | FEAT-NNN                             |
| **Status**       | Stable / Beta / Planned / Deprecated |
| **Endpoints**    | [list of METHOD path]                |
| **UI**           | [components/pages/routes]            |
| **Owners**       | [roles / actors who use it]          |
| **Dependencies** | [services, integrations]             |
| **Evidence**     | [code path(s)]                       |

**Capabilities:**

- [x] Implemented capability
- [ ] Missing or planned capability
```

### 3. `crud-matrix`: CRUD matrix

```markdown
| Entity | Create | Read | Update | Delete  | Evidence   |
| ------ | ------ | ---- | ------ | ------- | ---------- |
| User   | ✅     | ✅   | ✅     | ⚠️ Soft | api/users/ |
```

Legend: ✅ Full, ⚠️ Partial/conditional, ❌ Not available

### 4. `route-inventory`: API endpoint inventory

Grouped by domain. Columns: `Method | Endpoint | Purpose | Auth | Handler file`. The meaning of each route group (auth model, error semantics, journeys) belongs to the API map; cite its section ids instead of restating them.

### 5. `ui-inventory`: UI component inventory

Three sub-tables:

- **Forms**: `Page route | Form name | Submits to (endpoint) | Validation lib`
- **Dashboards / Views**: `Page route | View name | Data source endpoint(s) | Role gating`
- **Actions**: `Component | Type (modal/dialog/confirm) | Trigger | Endpoint called`

### 6. `integrations`: third-party integrations

| Service | Purpose | Package | Status | Features using it |
| ------- | ------- | ------- | ------ | ----------------- |

### 7. `flags-and-wip`: feature flags and WIP

**Active flags:**

| Flag | Description | Default | Environment | Read by (file) |
| ---- | ----------- | ------- | ----------- | -------------- |

**WIP signals (from git + grep):**

| Signal                 | Evidence                            | Estimated status |
| ---------------------- | ----------------------------------- | ---------------- |
| `feature/UPEX-XYZ-...` | Active branch, last push N days ago | WIP              |
| `TODO: implement X`    | path:line                           | Planned          |

### 8. `discovery-gaps`: discovery gaps

MANDATORY. List features that:

- Could not be verified from code
- Appear partially implemented
- Have unclear ownership or purpose
- Look deprecated but aren't formally marked as such
- Need team clarification before being scoped

Each gap should be actionable: what to ask, who to ask, or what to grep for next.

## Downstream consumers

This map is consumed (through `bun run context:map business-feature-context`) by:

- `/project-context master-plan` — uses the feature catalog and CRUD matrix to scope multi-story epics and identify gaps.
- `/project-context api` — cross-references the endpoint inventory section.
- `/sprint-development` (Planning step) — reads relevant domain section when scoping a story.

Keep section ids stable so downstream consumers can address them with `--section <id>`.

---

## Rules / constraints

1. **Read before write**: in UPDATE mode, read the existing map through `--list` / `--section`, regenerate only the stale sections and diff them. Never blind-overwrite, never change a section id.
2. **No silent deletions**: if a feature disappears between runs, surface it in the diff and explain why (likely deprecation or rename).
3. **Code is ground truth**: when PRD/SRS disagrees with code, code wins. Note the mismatch in **Discovery gaps**.
4. **Respect scope**: if `$ARGUMENTS` restricts scope, do NOT scan outside it — but DO note in the header which domains were skipped.
5. **No coverage / testing claims**: this is a dev-side feature inventory. Do NOT add test coverage matrices, ATC references, or QA-side relevance. Those live in the qa-side counterpart.
6. **Soft gates only**: if the data map is still a placeholder, continue and suggest running `/project-context data` next.
