01 · the problem

Today's TMSs are document vaults
with execution glued on top.

01 The same step, forty times

navigate to /login is copy-pasted across 40 test cases. Change the flow and you edit 40 places, or you miss 12.

02 Nobody knows what still holds

The product moves, the repository rots. Release by release, the suite drifts from the app and no one can point at which tests are still valid.

03 "What does this story cover?"

A manager asks. Nobody can answer with certainty. Traceability lives in a spreadsheet, a Confluence page, and someone's memory.

04 Bugs leave the QA loop

The TMS hands off to Jira the second something fails — so which ATC failed, in what run state, in which module, is lost.

And the deeper one: none of them teach QA engineering. They let you do bad QA quickly.

the problem02 / 15
Do not rush this slide. Every QA in the room has lived all four. Ask for a show of hands on #1. The punchline is the last line: the tools are neutral, so bad practice survives forever.

02 · the thesis

We attack the problem from the
data model, not the feature list.

An ATC cannot exist without a user story

Anchoring to a US and at least one acceptance criterion is a schema constraint, not a nice-to-have field. Orphan tests are rejected by the database.

A test cannot exist without ATCs

A Test is a chain of references. There is no free-text blob to paste steps into, so there is nothing to duplicate.

A bug cannot exist without a module

Every defect is anchored to where it lives. Which means the heatmap, the trends, and the coverage numbers are free.

The structure of the product teaches good QA simply by how it works. You do not need a process document to enforce it.

the thesis03 / 15
This is the slide to land hard. Competitors add features; Bunkai adds constraints. Constraints are what make a methodology stick. If someone objects "that's friction" — yes, deliberately, at authoring time, to remove friction at maintenance time.

03 · the primitive

ATC — Acceptance Test Case

A complete mini-flow: one precondition, one action, all the assertions that follow from it. Reusable, atomic, anchored.

ATC-014 UI Pass

Log in with valid credentials

anchored to BK-166 · AC-2, AC-3

1 Open /login
2 Fill email + password
3 Submit

Assertions

Redirected to the workspace home
Session cookie is set
  • Complete flow, never a single click. "Click the login button" is not an ATC. "Log in with valid credentials" is.
  • Identity = precondition + action. Same state, same trigger, more expectations? Same ATC, more assertions. This is what makes it atomic.
  • Layered. Every ATC declares UI, API, or Unit — so a chain can mix layers and a report can slice by them.
  • Written once, owned by one team. ATC-014 is the single definition of "log in" in the entire repository.

06 · execution

Three ways to run.
One data model underneath.

A regression report can be fed by any mix of the three, because all of them produce the same kind of Run against the same ATCs.

executor: human

Manual

Start a run against an environment, mark each step pass, fail or block, attach evidence, close with a verdict. Abort with a reason and the run is preserved, not deleted.

executor: agent

Agentic

An AI operator drives the exact same API a human drives. The agent is a first-class consumer of the product, not a chatbot bolted onto the side.

executor: ci

Automated

Your pipeline submits step results, or uploads a results file, and a Run appears linked to its commit and branch. Same ATCs, same reports.

Why this matters commercially: no other TMS treats the agent as a first-class executor, and none unifies the three streams into one regression view. The intelligence lives outside the app; the app is the operating surface.

execution07 / 15
Be honest about status: manual is shipped, automated ingestion is the next epic, agentic already works through the public API and personal access tokens. Do not oversell — the point is that all three land on the same table, which is the hard part and it is already done.

07 · defects

Bugs live inside the test cycle.

Filed from the failing step, anchored to module, ATC and run. The tracker gets a copy if you want one — it does not get ownership.

  • Filed in context. One action on a red step creates the defect with the run state already attached.
  • Categorised by construction. Module + severity + status are required, so the metrics are a byproduct rather than a reporting project.
  • Heatmap per module. Count and week-over-week trend, so you can see which part of the product is decaying, not just how many bugs exist.
  • One-way sync, optional. Jira stays in the loop for the people who live there. QA keeps the source of truth.

08 · coverage

Answers, not percentages.

"Eighty percent of tests pass" tells you nothing about whether the tests validate what matters. These four questions do.

What is untested right now?

Criteria and modules with no ATC bound to them, plus a not-run filter for what exists but has never been executed. Gaps become a list, not a feeling.

How long until this story is green?

Time-to-green per user story, computed from run and bug history. A real cycle-time number for the QA phase.

Show me the whole chain.

Story to criterion to ATC to test to run to bug evidence, rendered in one read and filterable by verdict, module and date range.

Can I hand this to an auditor?

Export the assembled chain as a read-only snapshot. Regulated teams get evidence, not screenshots pasted into a document.

coverage09 / 15
Read the four headings as questions the room already gets asked and cannot answer. That framing converts better than listing the features.

10 · origin

This did not start as a product.
It started as an architecture.

Bunkai is the productisation of KATA — the Component Action Test Architecture — and of the wider IQL methodology it belongs to.

  • IQL — Integrated Quality Lifecycle. Planning, documentation, execution and reporting as one traceable lifecycle. KATA is its automation arm.
  • KATA. A layered automation architecture where an ATC lives as a decorated method on a domain component, mapped one-to-one to a ticket.
  • The name closes the loop. A kata is the form. Bunkai is the practice of breaking that form down into the pieces you actually apply.

11 · the correlation

The same ATC, on both sides.

// KATA — LoginPage.ts, domain component (layer 3)
@atc('BK-166')
async loginWithValidCredentials(data: LoginData) {
  await this.page.goto('/login');
  await this.page.locator('#email').fill(data.email);
  await this.page.locator('#password').fill(data.pass);
  await this.page.locator('button[type=submit]').click();
  await expect(this.page).toHaveURL(/dashboard/);
}

One decorated method. One ticket. One complete flow.

In KATA (the code) In Bunkai (the product)
@atc('BK-166') method ATC entity, layer UI
Domain component file Module in the tree
Chain in tests/e2e/ Test — ordered ATC chain
Steps layer (3.5) Reused ATCs as a precondition prefix
Playwright execution Run, executor ci or agent
Reporter output Run results, coverage, heatmap

Write the automation in KATA, manage it in Bunkai. Same vocabulary, same identifiers, no translation layer between the framework and the test management system.

Why they cannot just copy it

Reusable ATCs are a data-model change, not a feature. Retrofitting them means migrating every customer's monolithic test case — and rebuilding the distribution model to ship self-hosted.

Who this unblocks

Fintech, healthtech and legaltech teams that cannot legally put specs and test data on someone else's SaaS. Data sovereignty is solved by ownership.

14 · appendix · for the curious

The part I said we would leave for last.

API-first, literally

REST with an OpenAPI contract as the source of truth, personal access tokens, and a CLI. The UI is one client among several — agents and pipelines are the others.

Multi-tenant by row

Isolation is enforced at the database layer, so a member is never notified about, or able to read, an entity outside their workspace.

Immutable run history

Runs snapshot the ATC content they executed. Editing an ATC propagates forward to tests, never backwards into recorded results.

Stack

Next.js on Vercel, Postgres with row-level security, typed end to end from the OpenAPI contract. A self-hostable distribution is the target for the community edition.

Where to dig

The domain glossary defines every term used in this deck. The data map, feature map and API map cover entities, screens and endpoints respectively. The KATA reference lives in the framework repository.

Everything above is a consequence of one decision: put the discipline in the data model.
