## 1. Executive summary

Bunkai's API is the **only** way state changes enter the system — there is no UI-only write path. Every action a QA engineer takes in the browser, every step result an AI agent posts at 02:00 UTC, and every Bug pushed from a CI runner ride the same `/api/v1/...` surface. This is the structural decision behind Bunkai's three-mode claim: **manual, agentic, and automated runs are indistinguishable in shape** because they all flow through the same endpoints, validators, and persistence layer.

The API is operated by two distinct consumer classes. **End users in browsers** sign in via Supabase Auth — **email + password is the primary rail** (ADR-0007), with email-OTP confirmation mandatory and OAuth a separate rail (ADR-0008) — carry a JWT in an HttpOnly cookie, and resolve workspace context implicitly from session state. **API operators** (the Bunkai CLI, AI agents, CI/CD pipelines — the Karim persona) issue **Personal Access Tokens** (`bk_pat_<prefix>.<secret>`, SHA-256-hashed at rest) and present them as `Authorization: Bearer ...` on every request. The capability vocabulary is exactly four strings — `atc:read`, `atc:write`, `run:execute`, `workspace:admin` (`lib/api/capabilities.ts`, mirrored by the `scopes` CHECK in migration `0008_access_tokens.sql`) — and layers on top of the workspace role hierarchy (`viewer ⊂ member ⊂ admin ⊂ owner`), so a `member` user can mint an `atc:read`-only token whose bearer cannot create ATCs even though the underlying user could.

A small number of conventions hold the surface together: a **bare-JSON success body with a `{ error: { code, message, details?, request_id? } }` failure envelope** (`lib/api/error-envelope.ts`), `Idempotency-Key` **opt-in per endpoint** (ADR-0002 — adopted today by `POST /api/v1/tests` and `POST /api/v1/runs`), cursor pagination on lists (`?limit` max 100, `?before=<cursor>`), and — as a **target, not a shipped control** — per-token rate limits. There is no app-level rate limiter yet; the only 429s in production are passthroughs of Supabase's own auth throttling (ADR-0007 point 5, documented follow-up). The spec is self-served at `GET /api/openapi` (`app/api/openapi/route.ts`); the same generated file is also reachable as the Next static asset `/openapi.json`. Either way an agent can read its own contract at runtime. Three critical journeys exercise the full surface end-to-end: first-time setup (Workspace → Project → Module → US/AC → ATC), manual run + bug capture, and AI-agent-driven run via Bearer auth.

## 2. Permission & auth model

> **Discovery phase**: Phase 1 — Permission & auth model. See §1 Permissions table + §5 sequence diagrams in `architecture-specs.md` for code-path anchors.

### 2.1 Tier table

| Tier                       | Who it applies to                                   | How to acquire                                                                                       | Where enforced (live code path)                                                                                                  |
| -------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **Public (unauth)**        | Anyone — pre-auth callers, OpenAPI spec consumers   | None — no token required                                                                             | `withApiHandler(handler, { auth: 'public' })` — no identity is resolved at all (see the enumerated set in §2.1.1)                |
| **End-user session (JWT)** | Browser-based QA engineers, leads, developers       | Sign in via Supabase Auth (email + password primary — ADR-0007; OAuth rail — ADR-0008) → JWT cookie  | `lib/api/principal.ts` `resolveIdentity()`, called **per route** by `withApiHandler` — NOT by `middleware.ts`                    |
| **Bearer PAT (token)**     | CLI, AI agents, CI pipelines, scripts               | `POST /api/v1/tokens` while cookie-authenticated → plain token returned ONCE; SHA-256 hash stored    | `lib/api/middleware/bearer.ts` `requireBearerToken()`, reached through the same per-route `resolveIdentity()`                    |
| **Role-gated (RBAC)**      | Any authenticated caller acting on workspace data   | Tier above + active membership in target workspace with sufficient role                              | Postgres **Row Level Security** on every table carrying `workspace_id` + route-handler guards for non-CRUD (invite, role change) |
| **Capability-gated**       | Any caller on a route declaring `auth: 'required'`  | Tier above + the caller holds every capability the route lists (`atc:read`, `atc:write`, …)          | `requireCapability()` in `lib/api/principal.ts`, run by the gateway BEFORE the handler body                                      |
| **Service-role (system)**  | Migrations, scheduled jobs, the run-timeout sweeper | Supabase service-role key (env-var, NEVER exposed to user agent)                                     | Server-only admin client (`lib/supabase/admin.ts`) — used only for secret-table access and other RLS-exempt paths               |

Role inheritance: `viewer ⊂ member ⊂ admin ⊂ owner`. Capability is **AND**-ed with role — a `member`-minted `atc:read`-only token cannot upgrade to write even within the user's own permissions. A **cookie** session implicitly holds all four capabilities (`ALL_CAPABILITIES`); a **PAT** holds the explicit subset stored in `access_tokens.scopes`.

### 2.1.1 The four route postures (ADR-0001)

`middleware.ts` does **not** authenticate the API. It only refreshes the Supabase cookie session and redirects unauthenticated browsers away from the protected page prefixes (`/home`, `/projects`, `/onboarding`, `/settings`, `/activity`). All API auth happens **per route**, inside `withApiHandler` (`lib/api/handler.ts`), which forces every route to declare exactly one of four postures — a route that declares none does not compile:

| Posture                        | Meaning                                                                     | Count (method×route) |
| ------------------------------ | ---------------------------------------------------------------------------- | -------------------- |
| `auth: 'required'`             | Authenticated **and** holds every listed capability                          | 67                   |
| `auth: 'authenticated'`        | Authenticated, no capability required (escape hatch, must state `why`)       | 9                    |
| `auth: 'public'`               | No identity resolved                                                         | 8                    |
| `auth: 'cookie-only'`          | Authenticated, **and a Bearer PAT is structurally rejected with 403**        | 4                    |
| (`bypass`)                     | Not a `withApiHandler` route at all (spec serving, OAuth callback, OPTIONS)  | 4                    |

Counts are the live census in `lib/api/route-capability-coverage.snapshot.json` — read that file rather than trusting these numbers, which drift with every new route.

**The four `cookie-only` routes** are the ones that surprise people, because a valid PAT gets a **403, not a 401**:

- `POST /api/v1/tokens` — a PAT must not mint a PAT (ADR-0001's deliberate exception)
- `DELETE /api/v1/tokens/{id}` — nor revoke one
- `POST /api/v1/me/active-workspace` — browser UI state
- `DELETE /api/v1/workspaces/{id}/membership` — leaving a workspace

**The public + bypass set** (everything else needs an identity): `POST /api/v1/auth/check-email`, `/auth/confirm`, `/auth/magic-link`, `/auth/resend`, `/auth/signin`, `/auth/signup`, `GET /api/v1/health`, `GET /api/v1` (index) — plus the bypass routes `GET /api/openapi`, `OPTIONS /api/v1`, `GET /auth/callback`, `GET /auth/oauth/{provider}`.

```
      |------------------------->| supabase.auth.signInWith |
      |                          | {OAuth | Otp}            |
      |                          |------------------------->|
      |                          |                          | (OAuth dance OR
      |                          |                          |  magic-link email)
      |                          |<-------------------------|
      |                          |                          |
      |   Set-Cookie: sb-access  |                          |
      |   (HttpOnly, Secure,     |                          |
      |    SameSite=Lax, 1h TTL) |                          |
      |<-------------------------|                          |
      |                          |                          |
      | subsequent request       |                          |
      |  Cookie: sb-access=...   |                          |
      |------------------------->|                          |
      |                          | middleware.ts:           |
      |                          |  - refresh cookie session|
      |                          |  - redirect off /home,   |
      |                          |    /projects, /settings… |
      |                          |    if not signed in      |
      |                          | withApiHandler (per API  |
      |                          |  route, NOT middleware): |
      |                          |  - resolveIdentity()     |
      |                          |  - build Principal       |
      |                          |  - RLS-guarded queries    |
      |                          |    via principal.db      |
      |                          |                          |
      |   200 { ...payload }     |                          |
      |<-------------------------|                          |
      |                          |                          |
      | (1h later)               |                          |
      | access token expired     | refresh via              |
      |                          | sb-refresh cookie (30d)  |
      |                          | → sliding renewal        |
      |                          |                          |
```

**Notes**: JWT is 1h access + 30d refresh, sliding renewal (NFR §2). Logout server-side-revokes the refresh token. CSRF tokens accompany Supabase Auth flows; subsequent API calls are exempt because the cookie is `SameSite=Lax` and the API has no third-party origin (same domain as the SPA).

### 2.3 Auth flow — API operator (CLI / agent / CI, Bearer PAT)

```
   Operator (CLI / agent / CI)   Next.js                 Postgres
   --------------------------    -------                 --------
      |                            |                         |
      | (headless bootstrap)       |                         |
      | POST /api/v1/auth/signin   |                         |
      |   { email, password }      |                         |
      |  → 200 with a freshly      |                         |
      |    minted PAT at pat.token |                         |
      |  (new account: signup 202  |                         |
      |   → confirm with the OTP)  |                         |
      |  NO device-code flow, NO   |                         |
      |  CLI package — neither     |                         |
      |  exists in this repo.      |                         |
      |                            |                         |
      | POST /api/v1/tokens        |                         |
      |   Authorization: COOKIE    |                         |
      |     ONLY — a Bearer PAT    |                         |
      |     is rejected 403        |                         |
      |   body: { name, scopes:    |                         |
      |     ["atc:read",           |                         |
      |      "atc:write"],         |                         |
      |     workspace_id?,         |                         |
      |     expires_at? }          |                         |
      |--------------------------->|                         |
      |                            | generate 32-byte random |
      |                            | secret; token shape is  |
      |                            | bk_pat_<prefix>.<rest>  |
      |                            | hash := sha256(secret)  |
      |                            |                         |
      |                            | INSERT access_tokens    |
      |                            |  (user_id, workspace_id,|
      |                            |   token_prefix, scopes, |
      |                            |   expires_at)           |
      |                            | INSERT                  |
      |                            |  access_token_secrets   |
      |                            |  (token_id, hash)       |
      |                            |------------------------>|
      |                            |                         |
      |   201 {                    |                         |
      |     id, prefix, scopes,    |                         |
      |     token: "bk_pat_..."    |                         |
      |     # SHOWN ONCE — store!  |                         |
      |   }                        |                         |
      |<---------------------------|                         |
      |                            |                         |
      | (every subsequent request) |                         |
      |                            |                         |
      | GET /me                    |                         |
      |   Authorization:           |                         |
      |     Bearer bk_pat_...      |                         |
      |--------------------------->|                         |
      |                            | withApiHandler gateway  |
      |                            | (per route, not global):|
      |                            |  SELECT * FROM          |
      |                            |   access_tokens         |
      |                            |   WHERE token_prefix = ?|
      |                            |  then compare sha256    |
      |                            |   against the sibling   |
      |                            |   access_token_secrets  |
      |                            |   row; reject if        |
      |                            |   revoked_at IS NOT NULL|
      |                            |   or expires_at < now() |
      |                            |------------------------>|
      |                            |  build Principal        |
      |                            |   {userId, workspaceId, |
      |                            |    capabilities, via}   |
      |                            |  UPDATE last_used_at    |
      |                            |                         |
      |   200 { ...payload }       |                         |
      |<---------------------------|                         |
      |                            |                         |
      | (rotation / compromise)    |                         |
      | DELETE /api/v1/tokens/{id} |                         |
      |--------------------------->|                         |
      |                            | UPDATE access_tokens    |
      |                            |   SET revoked_at = now()|
      |                            | → immediate invalidation|
      |                            |                         |
      |   204                      |                         |
      |<---------------------------|                         |
      |                            |                         |
```

**Notes**: No CSRF protection needed on Bearer requests (no cookies). Tokens are random 32-byte secrets — SHA-256 hash is sufficient (no Argon needed). The hash does **not** live on `access_tokens`; it sits in the 1:1 sibling `access_token_secrets`, revoked from the QA inspection roles at table level (migrations `0011_split_token_secrets.sql` / `0012_drop_legacy_token_hashes.sql`). `last_used_at` is updated on every successful auth for rotation UX (Discovery Gap G6 in `business-data-map.md`).

**Uniform 401 — by design, do not branch on a sub-code.** `lib/api/middleware/bearer.ts` collapses **every** bearer failure into one `unauthorized` / `"Invalid token."` response: missing header, malformed shape, unknown prefix, hash mismatch, revoked, expired. That is deliberate anti-enumeration, not an omission — there is no `TOKEN_EXPIRED` / `TOKEN_REVOKED` / `INVALID_TOKEN` sub-code and an agent must not be written to expect one. Error codes are **snake_case** and enumerated in `API_ERROR_CODES` (`lib/api/error-envelope.ts`).

### 3.1 Journey 1 — First-time setup: sign-up → workspace → project → modules → US/AC → first ATC

**Numbered narrative:**

1. **OAuth callback (Supabase-managed)** — Elena clicks the invite link → Supabase Auth completes OAuth with GitHub/Google → JWT issued in HttpOnly cookie. No Bunkai endpoint is hit during the OAuth dance itself; {{PROJECT_KEY}}-001 creates a default workspace on first verified login if no invite was accepted.
2. `POST /workspaces` `{ name }` → 201 `{ id, slug, role: owner, plan: community }`. _Why_: tenant root; everything else hangs off this id. _Side effects_: creator inserted as `owner` in `workspace_members`; `workspace.created` event emitted; activity_log row appended.
3. `POST /projects` `{ workspace_id, name, description? }` → 201 `{ id, slug }`. _Why_: separate apps-under-test inside one tenant. _RLS guard_: caller must be `member`+ in workspace.
4. `POST /modules` (multiple — one per Module in the tree) `{ project_id, name, parent_module_id? }` → 201 each. _Why_: build the taxonomy that defect heatmaps and coverage rollups depend on. _Server-side_: depth ≤6 guard, circular-parent check (a cycle returns **422 `validation_failed`** with `details.reason = "move_cycle"` — `app/api/v1/modules/[id]/route.ts`; there is no `MODULE_CIRCULAR_PARENT` code), materialized `path` column updated.
5. `POST /imports/jira` `{ project_id, jql }` → 202 `{ import_job_id }`. _Why_: bulk-import US + AC from existing Jira tickets instead of retyping. _Async_: handler enqueues a Vercel-cron-triggered worker that pulls Jira REST `search` in pages, parses Atlassian Document Format → Markdown, heuristically extracts AC bullets, dedupes by `external_id`. Client polls `GET /imports/{import_job_id}` until `status: succeeded`.
6. `POST /atcs` `{ title, module_id, user_story_id, acceptance_criterion_ids[], layer, steps[], assertions?, tags? }` → 201 `{ atc, steps, assertions }`. _Why_: the first authored ATC — the moment Elena understands the data model's structural enforcement. _Server-side_: single transaction inserts parent + child rows + M:N join; `atc.created` event; Realtime row broadcast to subscribed clients.

**Endpoints involved**: `POST /workspaces`, `POST /projects`, `POST /modules`, `POST /imports/jira`, `GET /imports/{import_job_id}`, `POST /user-stories` (or via import), `POST /acceptance-criteria` (or via import), `POST /atcs`.

**Entities touched** (see `business-data-map.md`): `workspaces`, `workspace_members`, `projects`, `modules`, `user_stories`, `acceptance_criteria`, `atcs`, `atc_steps`, `atc_assertions`, `atc_acceptance_criteria`, `activity_log`, `imports` (Discovery Gap G1 in data-map).

### 3.2 Journey 2 — Manual run + bug capture mid-flight

**Business purpose**: Elena runs the smoke regression before a deploy, hits a failure on ATC-005, files a bug with full context auto-populated, aborts the rest of the run because the failure blocks downstream steps. The defect heatmap reflects the new bug within 5s.

1. `POST /runs` `{ test_id, environment, executor: { type: "human", identity: "<user_id>" } }` with `Idempotency-Key` header → 201 `{ run_id }`. _Why_: start a Run instance. _Server-side_: single transaction creates `runs` header + full per-ATC and per-step skeleton (all `pending`); environment must exist in Project's environment list (Discovery Gap G3 in feature-map for the missing `/environments` API).

3. **On fail** — runner UI highlights "Report Bug" CTA. Side drawer opens pre-filled (`module_id` inherited from ATC, `steps_to_reproduce` auto-populated from executed steps, `atc_id` + `run_id` set).

5. `POST /runs/{run_id}/abort` `{ reason: "Blocking defect on dependent ATC" }` → 200 `{ run, status: "aborted" }`. _Why_: continuing is pointless when the discount affects downstream steps. _Server-side_: `runs.status` set terminal, remaining `run_steps` swept to `skipped`, `abort_reason` recorded.

**Endpoints involved**: `POST /runs`, `POST /runs/{id}/steps/{stepId}/result` (looped), `POST /bugs`, `POST /runs/{id}/abort` (or `/finish` for a non-blocking completion).

**Entities touched**: `runs`, `run_atcs`, `run_steps`, `bugs`, `activity_log`, `integrations` (for Jira sync), `module_defect_stats` (materialized view).

**Feature IDs**: FEAT-025 Start Run, FEAT-026 Report step result, FEAT-027 Abort Run, FEAT-031 File Bug from Run, FEAT-033 Defect heatmap, FEAT-034 Bug → Jira sync, FEAT-047 Realtime subscriptions.

### 3.3 Journey 3 — AI agent (Karim) drives a Run via API

**Business purpose**: A scheduled Playwright + Claude Code agent executes the nightly regression of TEST-008 against staging with no human in the loop. The resulting Run + Bug are **indistinguishable in shape** from Journey 2 — dashboards aggregate transparently.

**Numbered narrative:**

1. `GET /me` → 200 `{ user_id, email, active_workspace, memberships[] }`. _Why_: agent confirms its token is valid before doing anything destructive. _Failure mode_: a uniform 401 `{ error: { code: "unauthorized", message: "Invalid token." } }` — the agent fails loudly and notifies the operator, but cannot tell expired from revoked from bogus (anti-enumeration, §2.3).
2. `GET /tests/{test_id}?expand=atcs.steps,atcs.assertions` → 200 `{ test, atcs: [{ atc, steps[], assertions[] }] }`. _Why_: fetch the **entire** Test contract in one round trip — agent doesn't pay N+1 latency to discover what to execute.
3. `POST /runs` `{ test_id, environment: "staging", executor: { type: "agent", identity: "claude-code-nightly-v3" } }` with `Idempotency-Key: 2026-05-19-nightly` → 201 `{ run_id }`. _Why_: same start-run path as Journey 2, but `executor.type = agent`. _Idempotency_: retry with the same key returns the original `run_id` instead of creating a duplicate Run.
4. **Loop per step** — agent drives Playwright, uploads evidence (screenshot/video) to R2 via signed URL, then `POST /runs/{run_id}/steps/{run_step_id}/result` `{ status, duration_ms, evidence_url }`. _Critical_: same endpoint, same transaction, same Realtime broadcast as Journey 2. Mateo's dashboard cannot distinguish agent runs from human runs without inspecting `executor.type` metadata.
5. **On failure** — `POST /bugs` with same payload shape a human would submit (the Bug appears in the same dashboards, the same heatmap rolls it up).
6. `POST /runs/{run_id}/finish` `{ status: "failed", finished_at: <iso> }` → 200 `{ run }`. _Why_: explicit terminal call (agents don't have a UI "Abort" button; `/finish` is the agentic / automated terminal-state endpoint).

**Edge cases observed**:

- **Idempotency-Key collision** (retry with same key): returns the original `run_id`/`bug_id`/etc — bounded 24h replay window.
- **Concurrent human run on the same Test**: allowed; both Runs are separate records.
- **Agent abandons (process killed mid-Run)**: Run stays `running` until the sweeper cron times it out (default 4h, configurable) → Discovery Gap §6 below.
- **Rate limit hit**: 429 with `Retry-After` header; agent backs off.

**Endpoints involved**: `GET /me`, `GET /tests/{id}?expand=...`, `POST /runs`, `POST /runs/{id}/steps/{stepId}/result` (looped), `POST /bugs`, `POST /runs/{id}/finish`.

**Entities touched**: Same as Journey 2 — `runs`, `run_atcs`, `run_steps`, `bugs`, plus `access_tokens` (auth) and `idempotency_keys`.

**Feature IDs**: FEAT-025, FEAT-026, FEAT-030 Finish Run, FEAT-031, FEAT-040 OpenAPI spec, FEAT-041 Bearer-token auth, FEAT-042 CRUD endpoints, FEAT-044 Idempotency-Key, FEAT-047 Realtime.

## 7. Conventions & cross-cutting

> Cross-cutting facts that span every endpoint. Drawn from `api-contracts.yaml` info block, {{PROJECT_KEY}}-037-040, NFR §2.

### 7.1 Versioning

- URL-prefixed: `/api/v1/...`. Breaking changes ship as `/api/v2`.
- Additive changes (new fields, new endpoints) ship in place — clients tolerant.
- OpenAPI 3.1 spec is the contract; `bun run api:sync` regenerates client + server types.

### 7.2 Response envelope

There is **no `success` field and no `data` wrapper**. A success body is the resource itself, bare. Only failures are enveloped (`lib/api/error-envelope.ts`):

```json
{ "id": "...", "title": "...", "...": "..." }
{ "error": { "code": "validation_failed", "message": "Request body failed validation.", "details": [ ... ], "request_id": "..." } }
```

Error `code` is a stable **snake_case** identifier drawn from the closed `API_ERROR_CODES` set — `bad_request`, `validation_failed`, `unauthorized`, `forbidden`, `not_found`, `method_not_allowed`, `conflict`, `idempotency_key_required`, `idempotency_key_invalid`, `rate_limited`, the domain codes (`ac_outside_user_story`, `module_outside_project_subtree`, `steps_position_invalid`, `slug_collision`, `chain_empty`, `chain_mismatch`, `chain_invalid`, `no_executable_steps`, `environment_invalid`), plus `internal_error` / `upstream_error`. Agents branch on `code`, never on `message` prose. `request_id` echoes the `x-request-id` header so a caller can quote it in a bug report.

### 7.3 Idempotency ({{PROJECT_KEY}}-037, ADR-0002)

- Header: `Idempotency-Key: <max 64 chars>`.
- **Opt-in per endpoint, not global.** ADR-0002 scopes it deliberately. Today exactly **two** routes adopt it: `POST /api/v1/tests` and `POST /api/v1/runs` (both required, both via `lib/api/idempotency.ts`). Every other POST — including `POST /bugs` — accepts no `Idempotency-Key`.
- Run terminal transitions (`/runs/{id}/finish`, `/abort`, `/steps/{stepId}/mark`) need no key: the RPC's row lock makes the re-call naturally idempotent.
- 24h TTL; the same `(namespace, endpoint, key)` returns the cached `response_snapshot`.

### 7.4 Pagination

- Cursor-based on list endpoints: `?limit=<int, default 20 or 50, max 100>&before=<cursor>`.
- Response carries `next_cursor: string | null`.
- No offset pagination — avoids deep-page consistency issues at scale.

### 7.5 Rate limits (NFR §2) — TARGET, NOT SHIPPED

**No app-level rate limiter exists.** There is no per-token sliding window, no `Retry-After` emitter, and no edge rate-limit gate. The table below is the NFR **target**:

| Endpoint class            | Target limit      | Target 429 response            |
| ------------------------- | ----------------- | ------------------------------ |
| Write (POST/PATCH/DELETE) | 100 req/min/token | 429 + `Retry-After: <seconds>` |
| Read (GET)                | 600 req/min/token | 429 + `Retry-After`            |

What actually ships today: the only 429s are **passthroughs of Supabase's own GoTrue throttling**, mapped to the canonical `rate_limited` code on five auth routes (`check-email`, `signin`, `signup`, `confirm`, `resend`, `magic-link` — see `app/api/v1/auth/*`). ADR-0007 point 5 states this explicitly and files a dedicated app-level limiter as a **documented follow-up, separate story**; ADR-0007's consequences also note that `check-email`'s accepted enumeration tradeoff is *not* covered by GoTrue throttling and needs that limiter as its real mitigation. Agents should still handle 429 with back-off, but must not assume a documented per-token budget.

### 7.6 CORS / CSRF

- Same-origin SPA → minimal CORS needs (`*.bunkai.io` allowed; subdomain whitelist in CSP).
- HttpOnly cookies + `SameSite=Lax` → CSRF surface limited to OAuth callback (Supabase-managed CSRF token).
- Bearer requests carry no cookies → no CSRF concern.

### 7.7 CSP (NFR §2)

- `script-src 'self'` + nonces for inline.
- `connect-src` allowlist: Supabase URL, R2, Sentry, PostHog.
- Strict — no `unsafe-inline` or `unsafe-eval`.

### 7.8 Realtime ({{PROJECT_KEY}}-040) — adjacent surface, not REST

Supabase Realtime channels keyed by `project_id`:

| Table       | Subscribers                           | Use                                              |
| ----------- | ------------------------------------- | ------------------------------------------------ |
| `runs`      | Run runner UI, Project View dashboard | Live progress on the Run, status transitions     |
| `run_atcs`  | Run runner UI                         | Per-ATC verdict rollup (derived from steps)      |
| `run_steps` | Run runner UI                         | Per-step result push (replaces polling)          |
| `bugs`      | Defect heatmap, activity timeline     | New bug rolls up immediately into module heatmap |

Frontend subscribes via `@supabase/supabase-js`. Phase 2 introduces a dedicated WebSocket/SSE channel for the agentic protocol (`phase2.agentic_protocol` flag) — lower latency, bidirectional, vendor-neutral.

### 7.9 Soft-delete ({{PROJECT_KEY}}-039)

- `DELETE` endpoints on Modules / US / AC / ATC / Tests set `archived_at = now()`. Cascade to descendants.
- Listing endpoints filter `archived_at IS NULL` by default; `?include_archived=true` opts in.
- Hard-delete only via admin endpoint with confirmation header.

### 7.10 Audit-light ({{PROJECT_KEY}}-038)

- Every state-changing endpoint inserts an `activity_log` row: `{ actor_id, action, entity_type, entity_id, payload_summary, at }`.
- NOT compliance-grade — Enterprise audit log (immutable, exportable) ships Phase 3 via `enterprise.audit_log` flag.

| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |

| **Predictable failure envelope**                             | Success bodies are bare JSON; failures are always `{ error: { code, message, details?, request_id? } }` — one shape to parse on the error path                                                                          | `lib/api/error-envelope.ts`                                                            |

No device-code flow and no browser redirect at runtime                                                                                                                                      | {{PROJECT_KEY}}-034; §2.3 above                                                        |
| **Idempotency-Key on the two creation endpoints that need it** | Retry-safe by design where a duplicate would create real duplicate state — `POST /api/v1/tests` and `POST /api/v1/runs`. | **Full Test contract in one round trip**                     | `GET /tests/{id}?expand=atcs.steps,atcs.assertions` returns the entire script — no N+1 latency to discover what to execute                                                                                              | {{PROJECT_KEY}}-017; api-contracts.yaml `expand` query param                           |
| **Uniform 401 (deliberately NOT sub-coded)**                 | Every bearer failure — missing, malformed, unknown, mismatched, revoked, expired — returns the same `unauthorized` / "Invalid token." This is **anti-enumeration**: an agent cannot, and must not try to, tell them apart. Re-mint the token and alert a human | `lib/api/middleware/bearer.ts`                                                          |
| **`x-request-id` on every response**                         | Echoed into the error envelope's `request_id`; the agent quotes it and the log line is findable in one grep                                                                                                              | `lib/api/handler.ts`, `lib/api/request-id.ts`                                          |
| **Rate limits with `Retry-After`** — TARGET, NOT SHIPPED     | Intended affordance. | **Cursor pagination (not offset)**                           | Deterministic results across concurrent writes; agent does not skip rows under load                                                                                                                                     | `?limit` + `?before=<cursor>` on list endpoints                                        |
| **Stateless steps endpoint**                                 | `POST /runs/{id}/steps/{stepId}/result` carries the full state of one step result — no hidden in-flight state between calls                                                                                             | {{PROJECT_KEY}}-020                                                                    |
| **Audit-light captures executor identity**                   | `executor.identity` (e.g. `claude-code-nightly-v3`) is durably stored on `runs`; investigators can trace which agent did what                                                                                           | {{PROJECT_KEY}}-019                                                                    |

## 9. Versioning + breakage policy

- **`/api/v1` is the MVP contract.** Lifetime = at least until Bunkai Cloud GA + Community-edition GA (Phase 2). No breaking changes inside v1.
- **Breaking changes ship as `/api/v2`.** v1 stays supported in parallel for ≥6 months after v2 GA (notice via deprecation header).
- **Additive changes ship in place.** New fields on response objects, new query params, new endpoints — all go in v1 without bumping.
- **The OpenAPI spec at `/api/openapi` is the contract.** Drift between spec and implementation is a release-blocking bug. `bun run api:sync` enforces spec-to-types alignment.
- **Versioned per-edition**: Bunkai Cloud and Bunkai Community share the same `/api/v1` shape — the schema is the durable artifact across editions (architecture-specs.md §3 lock-in mitigation).

## 10. Discovery gaps

> Greenfield project — no live API exists yet. The gaps below were surfaced during synthesis from `api-contracts.yaml` v1.0. Wave-1 sibling (`business-feature-map.md`) found Gaps #1–#3 in its §10; this section adds API-surface-specific gaps and reiterates the cross-document ones for `/project-bootstrap` resolution.

### Gap #1 — Workspace invite lifecycle endpoints absent

{{PROJECT_KEY}}-003 covers invite **creation**, but `api-contracts.yaml` v1.0 exposes no `GET /workspaces/{id}/invites` (list pending), no `POST /workspaces/{id}/invites/{invite_id}/resend`, and no `DELETE /workspaces/{id}/invites/{invite_id}` (revoke). The 24h-expiry behavior implies users will hit expired-invite cases (Journey 1 alt-path documents this). **Resolution**: surface in v1.0 before `/project-bootstrap` — invite UX is MVP-needed. Also documented as Gap #2 in `business-feature-map.md`.

### Gap #2 — Integrations + Environments management API absent

`integrations` and `environments` tables exist in the ERD (`business-data-map.md` §2). Both surface in Settings UI screens (`business-feature-map.md` §5.1). Neither has a public endpoint in `api-contracts.yaml v1.0` — {{PROJECT_KEY}}-019 references `environment` enum, {{PROJECT_KEY}}-009/{{PROJECT_KEY}}-028 reference Jira credentials retrieved from "integration config", but the management API is missing. **Resolution path**: confirm whether these are Settings-only (Next.js Server Actions, never exposed as Bearer REST) or whether the CLI / agent persona needs them. If Karim is expected to manage environments and integrations from CI, they must surface as `/integrations` and `/environments` resources. Also documented as Gap #3 in `business-feature-map.md`.

### Gap #3 — Missing R/U/D/List for User Stories and Acceptance Criteria

`api-contracts.yaml` v1.0 documents only `POST /user-stories` and `POST /acceptance-criteria`. {{PROJECT_KEY}}-035 ("All FRs 001–032 exposed under `/api/v1/...`") implies GET, PATCH, DELETE, and List endpoints exist — but the contract file is incomplete. Agent persona (Karim) using `/openapi.json` at runtime will encounter 404s on assumed reads/updates. **Resolution**: surface in v1.0 during `/project-bootstrap` Step 1. Also documented as Gap #4 in `business-feature-map.md`.

### Gap #4 — Workspace `plan` setter missing

`workspaces.plan` ∈ {community, cloud, enterprise} is the license-gate mechanism (architecture-specs §1) but no FR or endpoint documents how it's set. Implicit assumption: provisioned out-of-band (manual SQL by founder for design-partners in MVP; Stripe webhook later). **Resolution**: confirm MVP plan = out-of-band provisioning; defer Stripe / billing endpoint to Phase 2. Also documented as Gap #6 in `business-feature-map.md`.

### Gap #5 — Run-timeout sweeper cron is journey-implied but not exposed

`user-journeys.md` §3 "Agent abandons" notes "a sweeper cron times it out after a configurable max_duration (default 4h)" — no FR documents this behavior and no admin endpoint exposes the configuration. **Resolution**: codify as cross-cutting FR (e.g. {{PROJECT_KEY}}-041 Run abandonment sweeper). Decide whether `max_duration` is per-Project, per-Workspace, or global, and surface as a settings endpoint or feature-flag value. Action item for `/product-management`. Also documented as Gap #5 in `business-feature-map.md`.

### Gap #6 — Bulk-edit endpoint declared but not specced

{{PROJECT_KEY}}-030 (Table view) mentions `PATCH /api/v1/{entity}/bulk` accepting `{ ids[], patch }`. The endpoint shape is described in `functional-specs.md` but is not present in `api-contracts.yaml v1.0`. **Resolution**: add to spec during `/project-bootstrap` Step 1, document permissible `{entity}` values (atc / test / run / bug) and `patch` payload constraints (which fields are bulk-editable per entity).

### Gap #7 — Token introspection endpoint missing

`GET /api/v1/tokens` lists my tokens (issuer-side), but no endpoint accepts a token and returns its scopes (introspection). Agents that receive a token via env var have no programmatic way to verify scopes without calling a protected endpoint and reading the 200 vs 403 response. **Resolution**: confirm whether `GET /api/v1/me` returning `capabilities` is the intended introspection path; otherwise consider RFC 7662-style `/auth/introspect` for Phase 2.

### Gap #8 — Realtime channel auth model undocumented

{{PROJECT_KEY}}-040 declares Supabase Realtime channels keyed by `project_id` for `runs`, `run_atcs`, `run_steps`, `bugs`. The Bearer-PAT auth model in `api-contracts.yaml` covers REST only — how an agent subscribes to Realtime channels via a PAT (vs end-user JWT) is not documented. **Resolution**: confirm whether Realtime is browser-only (end-user JWT) in MVP and agent push is polling-only until the Phase-2 WebSocket protocol lands.

### Gap #9 — `/me` security declaration

**Resolved.** `GET /api/v1/me` is `auth: 'authenticated'` and is the canonical "is my token valid?" endpoint. An invalid token returns the uniform 401 `unauthorized` / "Invalid token." — there is no `TOKEN_EXPIRED` sub-code and, by the anti-enumeration design in §2.3, there never will be.

### Gap #10 — Search endpoint and ATC list endpoint overlap

`GET /search` ({{PROJECT_KEY}}-031, command palette) and `GET /atcs?q=...` ({{PROJECT_KEY}}-011, ATC search) both serve full-text search use cases. The differentiation (cross-entity vs ATC-only) is clear at the spec level but should be documented to avoid client confusion about which to call. **Resolution**: clarify in OpenAPI descriptions during `/project-bootstrap`.
