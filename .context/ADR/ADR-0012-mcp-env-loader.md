# ADR-0012 — Every MCP server reads `.env` through one filtered varlock loader; the plaintext harness copies are retired

- **Status:** Accepted
- **Date:** 2026-10-05
- **Deciders:** Boilerplate owner (upex-galaxy): env-secrets spike owner decisions of 2026-10-05 (OD1 = b, `.env` stays the default; OD5 = c) and the conductor's shared launch design for the secrets wave (loader = `bunx -p varlock@<pin> varlock run --no-redact-stdout`). Ported from agentic-qa-boilerplate ADR-0011 (PR #111) by unit env-d-u5, which also closes the env-d-u4 follow-ups (the shell is not the only reader of `.env`, `setup:doctor` reports the provider) and adds the sensitivity lint the QA incident called for

## Context

A harness reads its MCP config and spawns its servers before any hook runs, with whatever environment the harness process has. A terminal launch through `bun run claude|codex|opencode` carries the `.env` values (ADR-0010); a desktop app or a natively launched supervised worker carries none, and there is no command line to wrap. Until now each host solved that differently:

- **Claude Code**: `.mcp.json` named `${VAR}`, and `bun run harness:env` copied each value into the `env` block of `.claude/settings.local.json` (on macOS/Linux the MAIN checkout's file, shared by every worktree).
- **OpenCode**: `opencode.jsonc` named `{file:.auth/opencode/VAR}`, and the same generator wrote one plaintext value file per variable, regenerated by `bun run worktree:provision`.
- **Codex**: every stdio server, context7 included, started through an unfiltered loader (`varlock run -- <server>`) that handed it the WHOLE `.env`, with `env_vars` naming what it needed.

Two of those were plaintext copies of every MCP secret on disk, readable by any agent and not covered by "never read `.env`". The third gave each server every credential in the file. With the secret manager of ADR-0011, the copies were also blind to the vault: a value that lived only there reached no desktop-launched server.

The Supabase server made the problem concrete. The configs mapped the app's URL, publishable key and server-side secret key into it (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`). Measured on `@supabase/mcp-server-supabase` 0.13.0: the package reads `SUPABASE_ACCESS_TOKEN` and nothing else from the environment, so the secret key travelled to an MCP child, and into two plaintext copies, for no use at all.

Measured in agentic-qa (varlock 1.20.0, scratch schema, throwaway values; its ADR-0006 ledger): `--filter A,B` injects only those items and strips an inherited schema key outside the list; validation is scoped to the filter; `--inject vars` leaves no `__VARLOCK_ENV` blob; an EMPTY inherited value shadows `.env` and fails validation; the filter holds under an outer `varlock run`; stdio stays byte-intact with `--no-redact-stdout`. Re-checked here (same pin, names only): the filter strips an inherited schema key outside it; the three servers of `.mcp.json`, spawned exactly as configured with a near-empty environment, complete the MCP `initialize` handshake through the loader; OpenCode 2.0.20 with an empty process environment reports a loader-launched Supabase server `connected`, its token coming from the schema files alone.

The QA run of the same change also produced the incident behind decision 4: `varlock load --agent` redacts only the items a schema marks `@sensitive`, and a scratch schema that declared a token without the mark printed its inherited value into a transcript.

## Decision

1. **One loader, every host.** Each MCP stdio server that needs `.env` values launches as `bunx -p varlock@<pin> varlock run --no-redact-stdout --inject vars --filter <its vars> -- <server>` in `.mcp.json`, `opencode.jsonc` and `.codex/config.toml` (`MCP_ENV_LOADER_*`, `mcpEnvLoaderArgs()` in `cli/lib/agent-compatibility-contracts.ts`). A server with no `.env` value (context7) launches bare on every host. The pin tracks the `varlock` devDependency, so no standalone binary is needed. Supabase's filter is `SUPABASE_ACCESS_TOKEN` alone; the dead mappings are gone.
2. **The filter is the contract.** It lists exact variable names and IS the server's `.env` dependency set: `agents:compat:check` compares it across the three hosts like any `${VAR}`. A loader-launched server takes nothing from the host (`${VAR}`, `{env:}`, `{file:}`, `env_vars`). Both rules, and "a stdio server that needs `.env` values launches through the loader", are errors in the boilerplate and warnings downstream, where the three configs are protected or bootstrap-only and only a hand edit can deliver the change; the warning names the exact launch. The legacy unfiltered Codex loader still parses and reads as out of date.
3. **The copies are retired, never silently.** `bun run harness:env` stops generating and becomes the migration: a copy equal to `.env` is deleted, a copy `.env` does not reproduce is moved to `.auth/harness-env-backup/<VAR>` (0600) and named, and a copy a legacy host config still reads stays until that config changes. The names the old Supabase mappings copied count as copies to retire. The command is KEPT (`prepare` calls `--placeholders`, which now only serves a legacy `{file:}` `opencode.jsonc`). `bun run setup` retires in Step 7d, `bun run setup:doctor` reports any copy left, `bun run setup --variables` prints a restart notice instead of regenerating, and `bun run worktree:provision` derives nothing from `.env`.
4. **The schema is the redaction contract, so it is linted.** `bun run vars:schema:check` (and with it `repo:check` and the pre-commit gate, now triggered by any root `.env*.schema`) fails when a key whose name matches `SECRET_NAME_PATTERNS` (`cli/lib/env-schema.ts`) in any schema varlock loads lacks `@sensitive`, is opted out, or uses a non-literal `@sensitive`. Static parse, varlock never runs. The constant, its list and the rule are the same as agentic-qa's (whole `_` segments, case-insensitive).
5. **The doctor names the secret source and its reach.** `setup:doctor` reports the provider, the overlay and the names it resolves from the vault, and states that vault values reach `bun run claude|codex|opencode`, every MCP server and `bunx varlock run -- <cmd>`, never a shell that sourced `.env` (direnv). `.envrc` stays optional, follows the varlock order (`.env` then `.env.local`) and never uses a value-printing varlock form.

## Consequences

- **Positive:** no MCP credential exists on disk outside `.env` (or the secret manager); a desktop or natively launched harness gets its values with nothing generated, from the vault too; each server sees only its own variables, and a missing value for one server no longer stops another; the Supabase secret key no longer reaches an MCP child; a `.env` change reaches the servers on the next session start with no regeneration step; a secret-looking key cannot be committed without the mark that keeps `--agent` output redacted.
- **Negative / trade-offs:** every server spawn pays a varlock resolution (with 1Password on desktop-app auth, an unlock prompt may land inside the host's MCP startup budget: unlock first). The loader needs `bunx` on the PATH the host gives the server, as the bare `bunx` launch already did. A Claude Code worktree session still reads the MAIN checkout's `settings.local.json`; its env block stays until the main checkout's own `.mcp.json` is on the loader and `bun run harness:env` runs there. A downstream project stays on the old shape, with its copies, until it edits its configs. The name lint can flag a non-secret whose name happens to carry a secret segment; the fix is the `@sensitive` mark, never an opt-out.
- **Neutral / follow-ups:** a shell CLI that needs a vault-only value runs as `bunx varlock run -- <cmd>`; nothing wraps the interactive shell itself.

## Alternatives considered

- **Keep generating the copies** — works for every launch, but it is two plaintext copies of every MCP secret the AI can read, and blind to the vault.
- **Retire `harness:env` outright** — breaks `bun install` (the `prepare` line) and leaves machines holding copies with no migration.
- **One unfiltered loader everywhere** (the previous Codex shape) — every server receives every credential, and one invalid value anywhere stops all of them.
- **Keep the Supabase URL and key mappings in the filter** — no server reads them, and the secret key would keep reaching an MCP child.
- **Make direnv resolve through varlock** — every value-capable form prints values to the shell (`varlock load --format shell`), which is what the `.envrc` rule forbids.
